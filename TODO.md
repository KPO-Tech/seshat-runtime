### H9. The plan-approval gate does not reach the user - fixed (verified)

**Fixed (2026-10-16).** `exit_plan_mode` is no longer in `isAlwaysSafeTool` / `isSafeWorkflowTool`; `permissions.planExitDecision` (Step 3.4 of the engine) returns an Ask carrying the plan preview, which the integrator shows through the host's prompt function. The question is skipped when the user already approved the plan in the review dialog (`modeexec.PlanApproved`). `ExitPlanModeTool.CheckPermissions` still denies while a submitted plan awaits review. The SDK hook to record an approval exists (`sdk.ApprovePlan`, `Session.ApprovePlan`). Tests: `TestExitPlanModeAsksTheUserToApproveThePlan`, `TestExitPlanModeIsNotGatedWithoutASubmission`, `TestExitPlanModeDoesNotAskAgainAfterTheReviewApproved`. The text below is the original report.

**Found and reproduced (2026-10-12).** `exit_plan_mode` is the one tool whose whole purpose is to hand control back to the user, and it does not. `ExitPlanModeTool.CheckPermissions` builds the message the user is supposed to decide on - "Approve this plan and start implementation?" followed by an 800-character preview of the plan - and `resolveToolPermissions` replaces that result with an `Allow` before any prompt bridge sees it: a bare `types.Ask` carries no `DecisionReason`, and the branch that preserves an ask only admits a `Rule`-sourced ask, a `safetyCheck`-sourced ask, or one from a tool implementing `RequiresUserInteraction`. Everything else reaches the function's final `default` branch, whose comment describes it as normalizing a non-allow result. `engine.isAlwaysSafeTool` then allows `exit_plan_mode` a second time, since it is listed there for the mode-flag reason described in its own comment. Reproduced end-to-end through the real orchestrator with the real tool in `onRequest` and `auto` modes: no error, the tool runs, `trace.LocalPermission` is `allow` with an empty reason. Pinned by `TestExitPlanModeApprovalDoesNotReachTheUser` (`internal/tools/system/plan/exitPlanModeApproval_test.go`), which asserts the wrong behavior on purpose so that fixing this forces the test to be inverted.

The consequence is that plan mode's read-only guarantee is advisory. `write_file` and `edit_file` deny outright while `ExecutionMode` is `plan` (CHANGELOG 1.4.0), but leaving plan mode is what grants that write access, and the model can leave it on its own. The only enforcement today is the UI-level `submit_plan` review dialog (`internal/seshattui/ui/dialog/plan_review.go`), which is real but depends on the model choosing to call `submit_plan` and then respecting the instruction to wait - `exit_plan_mode` can be called directly, and its own prompt's "Call this ONLY after submit_plan has been approved" is not enforced anywhere.

Three separate mechanisms were built to deliver this approval and all three are inert - worth knowing before trying to fix it again:

- `ExitPlanModeTool.Definition().RequiresPermission` is set to `true` and read by nothing. A repo-wide search finds only the field declarations (`internal/tools/contract/types.go:45`, `surface.go:45`) and one assignment of `false` in `internal/tools/registry/builder.go:102`.
- `ToolUseContext.RequestPrompt` (`internal/tools/contract/context.go:133`) is declared and never assigned anywhere, so no tool can ask anything through it.
- `ExitPlanModeTool.RequiresUserInteraction` returns `false`, documented as "the runtime already routes ask-decisions through the prompt bridge for non-agent sessions". That is the belief that hid the gap, and it is false for the reason above.

**Not a one-line change.** Routing the ask so it survives turns the tool into a permission-stage failure, and the SDK's own plan round-trip then never returns the session to `execute` even when its host prompt function answers `approved` (`TestPersistedSessionsCarryPlanModeAcrossRestore`, `pkg/sdk/client_test.go:1769` - the test failed exactly this way while the change was tried, with `PromptFn` returning `Value: true`). The fix therefore also needs the approval path to re-run the tool so its `ContextModifier` applies, which is the actual work of this item. Until then the two halves must not be changed separately.

**Partially fixed (2026-10-12) - the enforced half.** The condition this item is about - `exit_plan_mode` may only leave plan mode once the plan the user was shown has been approved - now holds, but as a *Deny* rather than as an `Ask`. A local `Deny` survives the permission stage (it is returned as a stage failure, and no `isAlwaysSafeTool` entry can override it: that heuristic governs only the engine's global probe, while the tool's own `CheckPermissions` is consulted separately), whereas the bare `Ask` described above is still replaced by an `Allow`. `submit_plan` records the submission (`execution.MarkPlanSubmitted`), the review dialog records the answer (`execution.MarkPlanApproved`, called from `SeshatWorkspace.ApprovePlan`), and `ExitPlanModeTool.CheckPermissions` denies while a submitted plan is unapproved - leaving the session in plan mode with the tool's own side effects untouched. Revising a plan after feedback clears the earlier approval, so a revised plan is reviewed on its own. `TestExitPlanModeDeniedWhilePlanAwaitsReview` fails when the gate is neutralized, and `TestExitPlanModeAllowedAfterTheUserApproves` / `TestExitPlanModeIsNotGatedWithoutASubmission` pin the two ways through.

What this does **not** fix: nobody is still *shown* the preview, so the ask above remains dead, and plan mode's read-only guarantee is still unbacked by any user decision when no plan was ever submitted. That last case is deliberate rather than overlooked - `submit_plan` is optional (disabled without a persistence hook) and sub-agent plans are auto-allowed, so gating either would block a path with no review surface and leave plan mode with no exit. There is also no way to approve a submitted plan outside the TUI: `MarkPlanApproved` has exactly one caller, and `pkg/sdk` exposes no approval entry point, so an SDK host that submits a plan and then calls `exit_plan_mode` is now refused with nothing to answer with. Adding that hook is the next step for this item.

The same family, **fixed (2026-10-12)**: `EnterPlanModeTool.CheckPermissions` returned `types.Ask("Enter plan mode to explore and design an implementation approach?")` - a gate that never existed, unreachable twice over (the discarded-ask branch above, plus the `isAlwaysSafeTool` entry, which is skipped only in `never` mode). It now returns `types.Passthrough` with a comment recording that the freedom is deliberate: entering plan mode is read-only, reversible, and reduces what the agent can do, so the checkpoint belongs on the plan itself rather than in front of the safe direction - the line Claude Code also draws, whose `EnterPlanMode` tool is documented as not requiring permission while its `ExitPlanMode` requires it. Behavior is unchanged (both shapes ended as an allow). Pinned by `TestEnterPlanModeIsPermissionFreeByDesign` (`internal/execution/enter_plan_mode_permission_test.go`).

### M2. The auto-mode classifier ignores project instructions and keeps no transcript - fixed (verified)

**Fixed (2026-10-10) - the security fallback:** `checkGlobalPermission`'s step 4.5 allowed every call in auto mode, including destructive ones, whenever `e.autoMode` was `nil` - the common case for any deployment that never calls `SetClassifier`/`SetAdvancedClassifier` at all, since wiring an ML classifier is optional. This was a separate, unconditional-allow code path that bypassed the already-correct `FailClosed` handling `auto.Mode.Classify` has for a classifier that errors mid-call. `NewEngine` now calls `ensureAutoMode()` at construction, so `e.autoMode` is never `nil` and step 4 (which defers to `auto.Mode.Classify`) always runs instead; step 4.5 is deleted as now-unreachable. Inside `Classify`, "no classifier was ever configured" is its own case, independent of `FailClosed` (which keeps its original meaning: a classifier that is configured but errors at classification time) - it asks a human in an interactive session, and denies in a headless one (mirroring the existing PowerShell/`request_permissions` fast-paths, and necessary because this result returns directly from `checkGlobalPermission` without passing through `applyModeTransformations`'s headless ask-to-deny conversion). Safe tools and safe workflow tools (`agent`, `task_*`, plan mode) are unaffected - they're still auto-approved before step 4 is ever reached. Tests: `TestMode_Classify_NoClassifierConfigured_AsksRegardlessOfFailClosed`, `TestMode_Classify_NoClassifierConfigured_Headless_Denies` (`internal/permissions/auto/auto_test.go`), `TestIntegratorAutoModeNoClassifierAsksInteractively`, `TestIntegratorAutoModeNoClassifierDeniesHeadless` (`internal/permissions/integration_test.go`).

**Fixed (2026-10-10) - deleted, not wired:** `SetSeshatMdProvider` (`internal/permissions/auto/seshat_md.go`) was never called, so the classifier never saw the user's `SESHAT.md` preferences through it. Wiring it the obvious way - next to `SetAutoModeProviderClient`, which every one of its three call sites invokes per-client, including `cmd/grpc`'s `newSDKClientFactory` that builds one per incoming request - would have made `seshatMdProvider` a process-wide global written and read across concurrent, unrelated gRPC requests: an unsynchronized data race under `-race`, and a cross-tenant leak of one project's `SESHAT.md` content into another's classifier calls. It was already fully inert (nil provider, `BuildSeshatMdMessage` always returning `nil`) and had no caller anywhere outside its own file except `classifier.go`'s `ClassifyWithTranscript`. Deleted `seshat_md.go` entirely (`SetSeshatMdProvider`, `GetSeshatMdContent`, `BuildSeshatMdMessage`, `HasSeshatMdContent`) and its one call site, rather than leave working-looking but multi-tenant-unsafe infrastructure for the next contributor to "finish" the same way. A correct version would thread the content per-call (e.g. through `ClassifierContext`), not through a package global - left undone rather than risked here.

**Fixed (2026-10-10) - wired the existing telemetry hook:** `LogParseFailure` existed but nothing called it, even though `classifier.go` already has three branches that detect an unparseable classifier response and return "blocking for safety" - exactly where this telemetry call belongs. Added it to all three (`runTwoStage`'s and `runThinkingOnly`'s stage-2-unparseable branches, `runFastOnly`'s stage-1-unparseable branch). Also removed the stale "Track classifier transcript for debug - not yet implemented" comment in `engine.go`: the feature it refers to (`BuildTranscriptForClassifier` and the `Tool`/`ToolRegistry`/`DefaultTool` apparatus in `transcript.go`) is a separate, more elaborate transcript-building design with its own tool-input-encoding interface that nothing in the real tool registry implements - an abandoned alternate to the simpler `BuildTranscriptFromMessages`/`SerializeTranscript` mechanism `classifier.go` already uses, not a pending task. Left in place undeleted (unconfirmed whether every part of it is safe to remove) but no longer described as "not yet implemented."

### M5c. Sub-agents always run in `bypass` mode, and two built-in types do not match their name - fixed (verified)

`agent_tool.go` (lines 441, 795, 935) started every sub-agent with `PermissionMode: types.PermissionModeBypass`, unconditionally - the parent's mode was never inherited, so `never` in the parent did not constrain the child.

**Fixed (2026-10-10):** added `subAgentPermissionMode(parentMode)` in `agent_tool.go`: a parent in `never` mode now spawns children in `never` too (that mode's own contract is "used for headless/background agents that cannot display UI prompts" - exactly what a sub-agent is). Every other parent mode (`onRequest`, `auto`, `acceptEdits`, `bypass`, `granular`) still spawns a `bypass` child, since there is no UI path today to show a synchronous sub-agent an interactive prompt. `Call` reads the parent mode from `input.ToolContextValue().PermissionMode` and threads the resolved mode into all three `RunConfig` construction sites (`runAgent`, `runForkAgent`, `runAgentInWorktree`).

The `plan` type had `write_file` and `edit_file` (`internal/agent/loader.go`) despite its own prompt never mentioning writing, and despite session-level `ExecutionModePlan` (fixed in M5e, same day) being strictly read-only - **fixed** by removing both tools and adding an explicit "YOU NEVER MAKE CHANGES" line to its prompt, matching `browse`'s and `verify`'s own style.

The `verify` type was never a general "check the result" reviewer - it validates agent definitions, security constraints and tool permissions, read-only - but `internal/agent/prompt.go`'s own model-facing example taught the model to use it for "run relevant tests and summarize failures or passes," which is unrelated to what it actually does. **Fixed** by replacing that example with one that matches `verify`'s real scope (auditing a custom agent definition for excess permissions) and moving the "run tests" idea off of `verify` entirely, rather than renaming the type - the bare string `"verify"` is a runtime contract any existing skill/workflow file could already reference by value, so renaming it would silently break those on disk for no benefit over fixing the misleading example.

**Also removed:** `internal/agent/verify.go`'s `SecurityChecker.ValidateAgent` was a fully-coded, Go-native re-implementation of exactly what `verify`'s system prompt asks the model to do in English (syntax/security/permissions/compliance/structure checks), with zero callers anywhere in the repository, including tests. Beyond being dead code, its rules were stale: `checkCompliance` flagged `bypass` + `general-purpose` as a *critical* violation, which is now the normal default for every sub-agent spawn (this same fix), and `checkSyntax` rejected any custom agent type the registry already supports as "unknown". Deleted rather than wired up or patched - wiring it up as-is would have reported today's correct, by-design behavior as a security violation.

**Found by a post-session regression audit, fixed (2026-10-11):** the `subAgentPermissionMode` fix above only covered `agent_tool.go`'s three `RunConfig` sites. Two other sub-agent spawn paths still hardcoded `types.PermissionModeBypass`, unconditionally, and were missed because they either didn't exist yet or weren't in the original bug list:
- `internal/tools/agents/skill_fork.go`'s `SkillForkRunner.RunForkedSkill` (the `context: fork` skill path, added by M5b in this same session - after the original 3-site scan, so M5c's fix predates this file). A session in `never` mode invoking a forked skill got a bypass sub-agent regardless. Fixed by adding a `parentPermissionMode types.PermissionMode` parameter to the `skills.ForkRunner` interface (`internal/tools/system/skills/skillTool.go`), passed from `SkillTool.Call`'s `input.ToolContextValue().PermissionMode`, and resolved with the same `subAgentPermissionMode` in `RunForkedSkill`.
- `internal/agent/runner.go`'s `RestrictSessionSkills` (used when a sub-agent's `AgentDefinition.Skills` is non-empty) swapped in a brand-new `NewSkillTool(nil)` with no fork runner at all, regardless of whether the session it replaced had one - any skill-restricted sub-agent that tried to fork a skill got "no fork runner is configured for this host," a silent capability loss, not a permission-mode bug but found alongside it. Fixed by adding a `ForkRunner skilltool.ForkRunner` field to `coreagent.RunConfig`, threaded through `restrictSessionSkillsIfDeclared`/`RestrictSessionSkills`, and set from the three `agent_tool.go` sites (`NewSkillForkRunner(eng)`) and from `internal/team/execution.go`'s session handler.

Tests: `TestSkillTool_ForkSkill_UsesForkRunnerWithFrontmatterFields` extended to assert the permission mode is received (`internal/tools/system/skills/skill_fork_test.go`).

**Found and fixed (2026-10-11), a separate, pre-existing gap (predates M5c - the original 3 call sites never included the background path):** `AgentTool.runAgentBackground` (the `run_in_background: true` dispatch) hands off to `internal/runtime/tasks.Manager.CreateAgentTask`, which had zero `PermissionMode` wiring - the background session got whatever the client's default permission mode is (typically `onRequest`), not the parent's. That matters specifically because the background session is created from the *same* `*engine.Engine` as the foreground one, which stores exactly one `promptFn` shared by every session it creates - an "ask" from the background agent would route through the same prompt mechanism the foreground session uses, not fail safely out of sight the way a background task should. (There is no actual hang risk: `permissions/integration.go`'s `effectivePromptFn(ctx) == nil` check already denies an ask with a generic error when nothing is listening - but that's an accidental safety net, not the intended behavior, and relies on the prompt simply not being wired rather than the background session being correctly scoped.) **Found and fixed (2026-10-11), a third gap in the same background-dispatch path:** `runAgentBackground` accepted `agentType` and `allowedTools` but only ever used `agentType` for display in the result (`"agentType": agentType`) - it was never resolved to actually pick a system prompt, unlike `runAgent`/`runForkAgent`/`runAgentInWorktree`, which all call `agentDef.GetSystemPrompt()` and `session.SetSystemPromptTemplate(sp)`. `agent({type: "browse", task: "...", run_in_background: true})` ran under the engine's default identity, never Browse's - the requested type had no effect on behavior, only on what the result claimed it was. **Found and fixed (2026-10-11), the bigger gap underneath the one above - no sub-agent tool restriction worked at all, for any spawn path:** dug into why, since this is security-relevant and deserved a real diagnosis before touching anything:

1. `RunConfig.ToolFilter` was meant to apply `allowedTools`/`agentDef.GetToolPatterns()` as a restriction, filtered via `filterToolsByNames(config.Tools, config.ToolFilter)` - but `config.Tools` was unconditionally `nil` at **every** `RunConfig`-constructing call site in the repo, not just the three in `agent_tool.go`: `spawn_agent.go`/`resume_agent.go` also pass `Tools: t.tools`, and `t.tools` is itself always `nil` at their only construction site (`pkg/sdk/client.go`: `NewSpawnAgentTool(queryEngine, nil, agentRegistry)`/`NewResumeAgentTool(queryEngine, nil, agentRegistry)`). Filtering `nil` by anything is always empty.
2. Separately, even with `config.Tools` populated, the registration step (`for _, t := range allowedTools { session.RegisterTool(t) }`) would have **failed outright** on any tool already present: `NewSessionFromState` populates `session.state.Tools` from the engine's full registry via `SurfaceBuilder.BuildToolMap` *before* `RunAgent` ever reaches this loop, and `Session.RegisterTool` errors on a duplicate name. The "register a filtered subset" design assumed a session that starts empty; that stopped being true once session creation started auto-populating from the registry.
3. The session's declared tool-surface profile (`ToolSurfaceProfileSubagent` vs the top-level `ToolSurfaceProfileMonoRun`) turned out to be a no-op *for every profile*, confirmed by checking `visibleInSurfaceProfile`: it returns `true` unless a tool's own definition sets `Metadata[toolSurfaceProfilesMetadataKey]` - and grepping the whole repo, zero tool definitions ever set that key. So profile-based filtering is dead too, independent of (1) and (2).

Net effect: every sub-agent, on every spawn path (synchronous, forked, worktree-isolated, background, skill-forked, spawned, resumed, or run from a workflow node), got the **entire** tool registry regardless of its own type's declared `Tools` list or an explicit `tools: [...]` restriction from the caller - those were accepted, validated, and otherwise ignored.

**Fixed** by replacing the broken "filter then additively register" approach with pruning what the session already has: a new `RestrictSessionTools(session, patterns)` (`internal/agent/runner.go`, next to the existing `RestrictSessionSkills`) unregisters every tool not matching one of `patterns` (wildcard-aware, reusing the existing `matchesPattern`). `RunAgent` now calls it with `config.ToolFilter` if non-empty, else falling back to `agentDef.GetToolPatterns()` - covering every caller that goes through `RunAgent` (`agent_tool.go`'s three sites, `skill_fork.go`, `resume_agent.go`, `spawn_agent.go`, `pkg/sdk/client.go`'s `RunAgentTask`) with one fix. `RunConfig.Tools` (now fully unused - confirmed its only read was the removed branch) and the two dead helpers `filterToolsByPatterns`/`filterToolsByNames` were deleted along with it, and the 5 call sites that set `Tools: nil`/`Tools: t.tools` were cleaned up. The background path (`tasks.Manager.CreateAgentTask`, which does not go through `RunAgent`) got the same treatment directly: a new `toolPatterns` parameter, resolved by `runAgentBackground` the same way the synchronous paths do, applied via the same `coreagent.RestrictSessionTools` after session creation.

Tests: `TestRestrictSessionTools_PrunesToPatterns`, `TestRestrictSessionTools_EmptyOrWildcardIsNoRestriction`, `TestRunAgent_AppliesAgentDefToolPatterns` (`internal/agent/runner_tools_restriction_test.go`) - the last one end-to-end through `RunAgent` with a real engine and two registered stub tools, confirming only the allowed one survives. Full `go build`/`go vet`/`go test -race`/`golangci-lint` all pass across the whole repository.

## Improvements taken from reading Codex (2026-10-17)

Not bugs: work decided after reading `helps/codex/codex-rs` (Apache-2.0). Files read: `ext/skills/src/render.rs`, `core/src/compact*.rs`, `prompts/templates/compact/`, `core/src/mcp_tool_exposure.rs`, `memories/`, `core/gpt_5_2_prompt.md`. Order is the order of work; the product owner asked for 1 to 5 first and wants to discuss 6 and 7 before anything is written.

1. **Skill catalogue budget.** Codex caps the catalogue at 2 % of the context window (at most 10,000 tokens, 8,000 characters when the window is unknown), truncates each description to 1,024 characters, and degrades by levels (full description, then name only, then a warning). Ours is unbounded: the `skill` tool description grows by about 40-80 tokens per skill.
2. **`get_context_remaining` tool and `context.usage` event.** Codex gives the agent a tool to read what is left of its window; the host shows the same number.
3. **Compaction.** Configurable threshold (Codex: `model_auto_compact_token_limit` plus an effective-window percentage); count tool schemas and provider-reported usage; keep the latest user messages (Codex keeps up to 20,000 tokens); put a hand-over sentence before the summary (`summary_prefix.md`); `pre_compact`/`post_compact` hooks already exist here; manual compaction in the SDK; start/finish events.
4. **MCP schema caps.** Codex limits a plugin tool schema to 8 KB and the plugin total to 64 KB. Add the same two limits so one chatty server cannot fill the context.
5. **Two-phase memory.** Phase 1 summarises each idle past session in the background (a no-op is allowed and preferred when nothing is reusable); phase 2 consolidates into a summary, a searchable registry and generated skills. Read path: summary injected, registry searched with a budget of 4-6 steps, drift-prone facts verified or flagged as memory-derived.
6. **General agent prompt** (to discuss): Codex's prompt has sections on autonomy and persistence, planning, validating the work, ambition versus precision, and how to present the answer.
7. **Single `apply_patch` edit tool** (to discuss): changes how the agent edits files.

Not in Codex, still ours to design: keyword search over skills (`skill_search`, a pinned handful, the rest searchable). Codex only budgets and degrades the catalogue.

## How this list was made, and its limits

Hand reading of `internal/engine`, `internal/runtime/memory`, `internal/permissions`, `internal/execution`, `internal/prompt`, `pkg/sdk` and the hook and event definitions, then a scan of `internal/`, `pkg/` and `cmd/` (excluding the `seshattui` fork and generated protobuf code) for functions, methods and constants whose name is referenced nowhere else. A name that appears anywhere counts as used, so the scan misses dead code that shares a name with live code: the real amount is probably larger. Items marked candidate have not been checked by hand. A static tool such as `deadcode` or `staticcheck` (U1000) would give a more exact list and could run in CI.
